# 书页调整动作与出刀节奏制作

本章以 `9001004 回忆协奏之刃` 的“长—中—更长”三次攻击为例，说明普通近战书页的调整、出手与收势。第 4 颗闪避保持原配置；不增加第四次攻击，不改威力、弃牌、伤害结算或全局游戏速度。

先读 [02_战斗书页完整制作](02_战斗书页完整制作.md)、[10_角色外观与特效系统](10_角色外观与特效系统.md) 与 [13_贴图攻击特效制作流程](13_贴图攻击特效制作流程.md)。本章控制动作何时发生，贴图制作仍按第 13 章执行。

## 1. 四个配置入口各负什么责任

| 字段 | 职责 | 本卡例子 |
| --- | --- | --- |
| `Motion` | 当前骰子的基础姿势，转换为 `ActionDetail`，并选对应皮肤动作 | J → Slash，H → Hit，Z → Penetrate，E → Evade |
| `ActionScript` | 按本次交锋结果组织双方 `MovingAction` 队列，配置动作、位移和反馈时点 | `Steria_MemoryConcerto_Long` |
| `EffectRes` | 攻击事件要创建的贴图或特效资源；动作脚本不应随意覆盖 | `Steria_AnhierTextureMemorySlash` |
| `Script` | 书页/骰子的游戏能力，依据所在 XML 层级挂接相应能力类 | 卡级 `AnhierDiscardAllPowerUp`；本卡骰级 Script 为空 |

改变 `Motion` 不能自动增加准备动作，延长贴图寿命也不会延长角色动作。准备姿势由 `ActionScript` 增加；本次使用通用 `Guard` 收刀架势，不依赖特定皮肤的 S1/S2。Guard 在这里只是姿势，不生成防御骰、护盾或防御效果。角色皮肤应提供与攻击明显不同的 Guard 图片。

## 2. Steria 实现与原版依据

可直接打开以下本地源文件核对：

- `SteriaBuild/BehaviourAction_Steria_MemoryConcerto.cs`：当前 Steria 实现。三个 ActionScript 入口按 Slash / Hit / Penetrate 设置独立准备和收势时长；不符合安全条件时回退到基类。
- `SteriaBuild/Verification/MemoryConcertoRhythm/`：针对双方队列、输赢、重投、取消与时序的本地契约检查。需要看真实原版调用方时，继续使用反编译的 `RencounterManager.cs`，不要从其他模组猜测队列规则。
- `SteriaBuild/Assembly-CSharp/AssemblyManager.cs`：按 `BehaviourAction_` 前缀扫描、去前缀登记，再依据 XML 创建实例。
- `SteriaBuild/Assembly-CSharp/RencounterManager.cs`：`SetMovingStateByActionResult`、`GetBehaviourAction`、`GetMovingActionWinMelee`、`GetMovingActionLoseMelee`、`MoveRoutine` 与 `MovingAction`。
- `SteriaBuild/Assembly-CSharp/EffectTiming.cs`、`ActionDetail.cs`、`CharMoveState.cs`：以本仓库游戏版本的命名枚举为准。

Steria 当前实现直接使用 `EffectTiming.PRE` / `NONE` 等命名枚举；这些是反馈时点，不是秒数。准备、出手和收势的持续时间通过各个 `MovingAction.delay` 表达。修改前应对照当前游戏反编译源码中的 `EffectTiming` 和 `MoveRoutine`，并用 Steria 的队列检查验证。

## 3. 三击时长与 XML 绑定

| 骰子 | 原数值/姿势 | 调整姿势，秒 | 出手段，秒 | 收势段，秒 | 最低合计，秒 | ActionScript |
| --- | --- | --- | --- | --- | --- | --- |
| 1，长 | Slash / J，2–7 | Guard / Stop，0.30 | 原生 Slash / MoveForward，0.15 | 原生 Slash / Stop，0.35 | 0.80 | `Steria_MemoryConcerto_Long` |
| 2，中 | Hit / H，3–6 | Guard / Stop，0.10 | 原生 Hit / MoveForward，0.15 | 原生 Hit / Stop，0.25 | 0.50 | `Steria_MemoryConcerto_Medium` |
| 3，更长 | Penetrate / Z，4–8 | Guard / Stop，0.50 | 原生 Penetrate / MoveForward，0.15 | 原生 Penetrate / Stop，0.55 | 1.20 | `Steria_MemoryConcerto_Final` |
| 4 | Def / Evasion / E，1–6 | 原生 | 原生 | 原生 | 不配置 | 空字符串 |

这些是缩放游戏时间中的**段最短时长**。原版等待双方该段移动结束，且存在逐帧 yield、骰子 UI、交锋间隔与游戏倍速，0.80/0.50/1.20s 不能当成实机墙钟承诺。三击标称最低总和为 2.50s；演示另接 0.25s 的原生闪避样例，不代表所有闪避场景都持续 0.25s。

本卡保持已有三个 EffectRes，实际绑定如下：

```xml
<Behaviour Min="2" Dice="7" Type="Atk" Detail="Slash" Motion="J"
  EffectRes="Steria_AnhierTextureMemorySlash" Script=""
  ActionScript="Steria_MemoryConcerto_Long" Desc="" />
<Behaviour Min="3" Dice="6" Type="Atk" Detail="Hit" Motion="H"
  EffectRes="Steria_AnhierTextureMemoryHit" Script=""
  ActionScript="Steria_MemoryConcerto_Medium" Desc="" />
<Behaviour Min="4" Dice="8" Type="Atk" Detail="Penetrate" Motion="Z"
  EffectRes="Steria_AnhierTextureMemoryPierce" Script=""
  ActionScript="Steria_MemoryConcerto_Final" Desc="" />
<Behaviour Min="1" Dice="6" Type="Def" Detail="Evasion" Motion="E"
  EffectRes="" Script="" ActionScript="" Desc="" />
```

## 4. 可复用入口与构建方式

生产源码是 `SteriaBuild/BehaviourAction_Steria_MemoryConcerto.cs`。三个公开、无参数构造的入口继承共用基类 `SteriaMemoryConcertoAction`。辅助基类故意没有 `BehaviourAction_` 前缀，以免被自动登记。不要为普通 ActionScript 新加 Harmony 注册补丁。

例如当前长击入口是：

```csharp
public sealed class BehaviourAction_Steria_MemoryConcerto_Long : SteriaMemoryConcertoAction
{
    protected override ActionDetail AttackMotion { get { return ActionDetail.Slash; } }
    protected override LOR_DiceSystem.BehaviourDetail AttackDetail
    { get { return LOR_DiceSystem.BehaviourDetail.Slash; } }
    protected override float Preparation { get { return .30f; } }
    protected override float Recovery { get { return .35f; } }
}
```

在其他普通近战骰上复用时，选择匹配动作的入口：Long 对应 Slash/J，Medium 对应 Hit/H，Final 对应 Penetrate/Z。入口检查实际动作和骰子细节，错绑会回落原生，不会偷偷改成另一种攻击。若需要“中时长斩击”，新建独立的、前缀正确的具体类，配置 Slash 与所需时长，不能把本卡 Medium 的 Hit 合同改掉。只有相同动作与时间需求才直接共用入口。

不按“这是第几次命中”计数，而由每颗骰自身携带脚本。因此第一击输掉拼点后，第二、第三击仍采用自己的中/更长节奏；重投、复制骰和多名角色使用也不会串位。新增入口若要允许相互交战时使用节奏，还需按其真实 Lose 行为审查 `HasDefaultLoseScript` 白名单。

## 5. delay、PRE、POST 与 NONE

构造函数的顺序是：

```csharp
new RencounterManager.MovingAction(
    ActionDetail.Guard,  // 本段开始就切换的姿势
    CharMoveState.Stop, // 本段位移方式
    0f,                // dstRatio，位移距离比例
    false,             // updateDir，动作后是否更新朝向
    .30f,              // delay，本段最短持续时长
    1f);               // speed，位移速度，不是整张书页播放速度
```

| 时点 | 实际含义 | 本次使用 |
| --- | --- | --- |
| `PRE` | 当前段开始时打印反馈 | 仅自身第一原生攻击段 |
| `POST` | 双方该索引段均结束后打印反馈 | 不使用 |
| `NONE` | 本段没有显式反馈时点 | 调整与收势，以及对手列表 |

`SetEffectTiming(atk, recover, damaged)` 的顺序为攻击特效、恢复显示、伤害显示。出手段恰好一次 `PRE, PRE, PRE`。前后段均为 `NONE, NONE, NONE`，不创建新攻击、不手动结算伤害、不强制播放第二份效果。`customEffectRes` 保持原生空值，继续使用 XML EffectRes；`callAtkEffectEvent` 保留原生值。

两个常见错误必须避开：

1. **只增大攻击段 delay。** 姿势和 PRE 已在该段开始发生，这只加长保持，不能构成前摇。正确方法是先插入独立、无事件的 Guard 段。
2. **所有段都设 NONE。** `MoveRoutine` 发现双方都没有显式事件时，会在动作循环前直接 `PrintEffect/PrintRecovery/PrintDamage`，导致准备阶段已经出现刀光。必须在自身出手段保留唯一 PRE。

原版只在 winner 队列消费 PRE/POST，所以不能把唯一事件放在 opponent 上。原版的 afterAction/succeedAtk/takeDamage 回调仍在动作循环之前执行；本章只调整已经结算结果的视觉显示时点，不重新安排能力结算。

## 6. 双方队列同步与回退

原版按相同索引同时开始双方动作，等双方都结束才移除本段。应先取得双方基类原生队列，确认是可处理形状，再包装；不要把所有移动统一改成 Stop。

| 索引 | 自身 | 对手 |
| --- | --- | --- |
| 0 | Guard / Stop，相应准备时长，无事件 | Default / Stop，相同准备时长，无事件 |
| 1 | 原生攻击首段，保留距离、速度、方向等参数，最低 0.15s，唯一 PRE | 原生受击或其他反应，原参数原样保留 |
| 2 | 原生攻击末段 Stop，延长为收势时长，无事件 | 若有第二原生段则保留；若原本只有一个 Knockback，另建同姿势 Stop 保持 |

单个受击对象不能放入两个索引：否则会击退两次且共享 elapsed。尾段需要新建 Stop，不能复制 Knockback。对手的 Damaged/Knockback 必须从自身出手段才开始，准备期间保持 Default。

正常近战 Win（包括无骰对手的单方面攻击）才包装。Lose/Draw、近对远、群攻/特殊 range、错误动作/类型、skip、blocked 以及外来动作事件均回落基类。已存在对手队列时不 Clear、不覆盖。对手带未知 ActionScript 时也回落，让原版继续调度它的专属失败动作；只有本卡三入口因 Lose 明确回基类而可列入白名单。

未知原生队列形状不截断：自身必须是预期的 MoveForward + Stop，对手须有 1–2 段，已有显式事件时也回落。第 4 颗闪避不绑定本类，继续沿用原版可重复闪避、储存与交锋规则。

## 7. 聚焦验证与动态预览

从仓库根目录执行；需要 .NET 8、Python 3、Pillow、NumPy 与 imageio-ffmpeg。预览用 imageio-ffmpeg 自带的 H.264 编码器，避免 PATH 中不含 libx264 的 FFmpeg。

本地还必须已有 `SteriaBuild/Assembly-CSharp/` 反编译参考树：该目录被 `.gitignore` 忽略，不随 Git 克隆分发；`prepare.py` 读取其中的原生方法，fixture 直接链接其基类和枚举。新环境需自行从对应游戏版本准备该参考树，并按 [08_编译与部署](08_编译与部署.md) 配齐 `SteriaBuild/Libs/` 游戏引用与 .NET Framework 4.7.2 SDK/目标框架支持，才能完成正式 Release API 编译。仅安装 .NET 8 或克隆仓库不足以满足这些依赖。

```powershell
python SteriaBuild/Verification/MemoryConcertoRhythm/prepare.py
dotnet run --project SteriaBuild/Verification/MemoryConcertoRhythm/MemoryConcertoRhythm.csproj -c Release -- .
python SteriaBuild/Verification/MemoryConcertoRhythm/render_preview.py
python SteriaBuild/VFXSource/AnhierTextureCombat/verify_source.py
dotnet build SteriaBuild/Steria.csproj -c Release --nologo
```

第一步先验证精确 XML 和四骰数值，再从反编译源提取 `RencounterManager` 的 13 个原生方法/类型块至 `output/memory-concerto-rhythm/generated/`，记录来源哈希。小型 net8 fixture 直接链接正式动作源码、原生基类/枚举与这些方法，仅以 shim 提供位置和结果容器；不复制一套自定义原生队列算法。

检查覆盖：三入口自动注册形状、前三 XML、唯一 PRE、准备无受击、单方/对攻击/对守备、原生距离与方向参数、击退次数、输平/远程/特殊脚本回退、重入、重投与并发实例。`queues.json` 来自正式 `GetMovingAction` 返回值；预览从该 JSON 读取全部三击时长和事件，不另写一张节奏表。

主要产物均在 `output/memory-concerto-rhythm/`：

- `queues.json`、`native-extraction.json`：双方实际队列、事件时点与原生来源。
- `rhythm-60fps.mp4`、`rhythm-30fps.gif`：正常速度完整三击及原生闪避边界。
- `phase-contact.png`、`phase-*.png`：每击调整、出手和收势抽帧。
- `preview-index.json`：精确队列哈希、媒体时长和抽帧时间。

**证据边界：** 这是正式队列驱动的 CPU 姿势示意，不是 Unity 或游戏录像。中性人体、位移插值、贴图挂接位置与 alpha 叠加均只用于读懂节奏；未执行游戏 MoveRoutine、碰撞、摄像机、音效、原生移动完成等待或完整骰子 UI。真实角色艺术优先在加载实际资源的 Unity 模拟工程中检查；本示意未覆盖的完整场景体验明确留待外部验收，必要时才做具体游戏内检查。未改素材可复用第 13 章既有资源验收，不要将本图当成特效渲染质量的新证明。

旧 VFX 验证器只额外允许 `9001004` 前三骰的三个**精确** ActionScript，逆转为空后继续比较原 canonical XML 哈希，既有 `accepted-six-baseline.json` 和 `accepted-tide-attacks-baseline.json` 不重录。若其他任务并发改了 CardInfo，旧全 XML 锁仍会报告 FAIL：应定位并单独验收该差异，不能为凑 PASS 泛化允许任意 ActionScript/EffectRes 或更新整表基线。

## 8. 构建、仓库包与游戏部署

Release API 编译的产物位于 `SteriaBuild/bin/Release/net472/Steria.dll`，证明本仓库游戏 DLL 的类与成员签名可用。fixture 输出是验证程序，不能代替这个 net472 DLL。

验收后将**同一候选**的 Release DLL 同步至仓库模组包 `SteriaBuild/SteriaModFolder/Assemblies/Steria.dll`，并核对 SHA256。只更新 CardInfo.xml 而保留旧 DLL 会造成新 ActionScript 无法解析；同步前备份，保证 DLL/XML 成对交付。此处描述交付步骤，是否已经同步以本轮验收报告为准。

游戏安装目录是另一层部署，按 [08_编译与部署](08_编译与部署.md) 核对最新 Player.log 或进程实际路径。当前文档记录 D 盘为实际游戏、C 盘可能是链接别名；不要凭路径拼写认为部署了两份。部署同候选 DLL 与 CardInfo.xml 后比对哈希。优先在模拟工程中依次检查三次 Win、首击 Lose 后后两击 Win、近对远和末闪避，将调用顺序、时点及脚本解析结果写入本次主日志并读取分析；只有无法模拟的具体交互问题才进游戏核对。

本功能仅改动作 C# 和三个 XML 字段，没有贴图、Shader 或 AB 修改，不需要为它重建 Unity/AssetBundle。构建成功、仓库包同步、游戏目录部署和实机验证是不同证据，不互相替代。
