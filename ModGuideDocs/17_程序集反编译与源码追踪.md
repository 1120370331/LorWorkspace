# 游戏程序集反编译与源码追踪

本章记录在《废墟图书馆》模组开发中查看游戏 API、定位原版行为和核对 Harmony 补丁签名的常用流程。反编译结果用于理解和验证；模组代码仍写在自己的项目中，不直接改写游戏程序集。

## 一、工具与各自用途

| 工具 | 用途 | 本仓库中的位置或版本 |
|------|------|----------------------|
| dnSpy | 交互式查看程序集、类、方法、字段、继承关系和 IL；适合沿类型树和引用关系追查 | 本机工具在 `dnspy/dnSpy.exe`，版本 v6.1.8；该目录被 Git 忽略，不随仓库分发 |
| ILSpy 命令行 | 按类型输出反编译代码或 IL，也可导出临时项目，适合精确、可复现的查询 | `ilspycmd`；当前工作站版本 9.1.0.7988。其他机器需要单独安装 |
| AssetStudio | 浏览 Unity 的 `.assets`、AssetBundle、Prefab、材质和贴图；它不是 C# 反编译器 | 本机工具在 `AssetStudio.net472.v0.16.47/`，不随仓库分发 |
| UnityPy | 用脚本批量读取 Unity 序列化资源、依赖、Sprite 和动画元数据 | 资源参考脚本见 `SteriaBuild/VFXSource/NativeAttackReference/`，依赖定义在其 `requirements.txt` |
| `rg` | 在已导出的 C# 文件中定位类型、方法名和调用点 | 推荐配合 `--no-ignore` 搜索仓库忽略的本地反编译缓存 |

如果当前机器尚未安装 ILSpy 命令行，可安装固定版本以便复现本章命令：

```powershell
dotnet tool install --global ilspycmd --version 9.1.0.7988
```

dnSpy 和 ILSpy 负责托管程序集代码；AssetStudio 和 UnityPy 负责 Unity 资源数据。分析一个攻击效果时，通常先从 C# 中查资源路径和加载逻辑，再用 AssetStudio 或 UnityPy 查看对应 Prefab、Sprite、材质与动画，不要把两类工具的作用混在一起。

## 二、选对程序集

废墟图书馆的游戏逻辑主要在游戏目录的 `LibraryOfRuina_Data/Managed/Assembly-CSharp.dll`。Unity API 位于同目录的 `UnityEngine*.dll`，BaseMod 与 Harmony 位于对应模组的 `Assemblies/` 目录。

本机已核实的游戏目录见[编译与部署](08_编译与部署.md)。先依据最新 `Player.log` 或正在运行进程确认实际安装位置，再将路径赋给 `$gameManaged`：

```powershell
$gameManaged = 'D:\Game Center\Steam\steamapps\common\Library Of Ruina\LibraryOfRuina_Data\Managed'
$gameAssembly = Join-Path $gameManaged 'Assembly-CSharp.dll'

Get-Item -LiteralPath $gameAssembly | Select-Object FullName, Length, LastWriteTime
Get-FileHash -LiteralPath $gameAssembly -Algorithm SHA256
```

不要只凭文件名认定程序集版本。本仓库 `SteriaBuild/Libs/Assembly-CSharp.dll` 是项目编译引用副本，当前文件可能落后于已安装游戏；使用前将它和实际游戏文件的长度、版本及 SHA-256 对照。需要核对新 API 时，以正在运行的游戏目录中的文件为准。Unity 模块、BaseMod 和 Harmony 也要来自对应的游戏与加载器版本。

## 三、交互式追查：dnSpy

1. 在 dnSpy 中打开实际游戏的 `Assembly-CSharp.dll`。需要检查依赖类型时，再打开同一 `Managed/` 目录中的 Unity 程序集或模组目录里的 BaseMod、`0Harmony.dll`。
2. 按类名或方法名搜索，例如 `BattleUnitModel`、`GetDiceResultValue` 或 `AttackEffectInfoManager`，进入具体声明。
3. 检查方法的完整参数、返回值、静态/实例属性、访问级别、重载、虚方法关系和调用位置。必要时切换到 IL 视图，确认反编译成 C# 后不直观的分支、异常路径或编译器生成代码。
4. 对基类、接口实现、调用者和字段读写继续追踪。不要只读到第一个同名方法就开始写补丁。

dnSpy 的“Analyze/分析”功能可用于查看成员的引用、实现或派生关系。不同版本菜单位置可能略有不同。只查看游戏程序集即可，不要使用模块写回功能修改安装目录中的 DLL。

## 四、可复现查询：ILSpy 命令行

输出单个类型的反编译 C# 到终端：

```powershell
ilspycmd -t 'BattleUnitModel' $gameAssembly
```

查看同一类型的 IL，用于区分重载、确认真实分支或核对编译器生成结构：

```powershell
ilspycmd --ilcode -t 'BattleUnitModel' $gameAssembly
```

如果类型位于命名空间中，`-t` 后填写完整类型名，例如 `Some.Namespace.TypeName`。需要临时导出完整程序集项目时，写到仓库之外，避免把整个游戏源码误提交：

```powershell
$decompileDir = Join-Path $env:TEMP 'LibraryOfRuina-Decompiled'
ilspycmd --nested-directories -p -o $decompileDir $gameAssembly
```

本仓库已有一个本地反编译缓存 `SteriaBuild/Assembly-CSharp/`，被 `.gitignore` 忽略。它适合快速文本搜索，但必须先确认它来自当前游戏版本。由于目录被忽略，使用 ripgrep 搜索时要显式允许忽略文件：

```powershell
rg --no-ignore -n -g '*.cs' 'GetDiceResultValue|AttackEffectInfoManager' SteriaBuild/Assembly-CSharp
```

需要检查一个类型时优先按类型导出或在 dnSpy 中查看；只有问题确实依赖跨程序集全局引用时，才导出整个项目。

## 五、从行为问题追到补丁点

按下面顺序记录证据，可以减少误补错重载或错误时点：

1. **定义现象和入口。** 从 `CardInfo.xml` 的 `Script`、`ActionScript`、`EffectRes`，自有模组的注册，或日志中的方法名开始；先区分数据入口、运行时回调和资源加载入口。
2. **找目标声明。** 用 dnSpy 搜索类/方法，或用 `ilspycmd -t` 输出类型；确认真实签名、所有重载、可见性和继承关系。
3. **沿调用链追踪状态。** 查看谁创建对象、何时写入字段、回调何时触发、成功/失败分支如何处理，以及取消、销毁和异常时如何清理。
4. **核对 Harmony 绑定。** 补丁使用的参数类型、返回值、实例/静态属性必须和原方法一致。存在重载时，使用精确目标选择；不要依赖只写方法名的模糊绑定。方法签名还应和当前游戏程序集的 API 编译检查一致。
5. **区分静态结论和运行时结论。** 反编译能证明程序集包含什么分支，不能单独证明它在实际战斗中的调用顺序、Unity 对象生命周期或加载路径。涉及时序和状态时，再用有界托管夹具、日志或实际游戏路径验证。

对于特效资源，继续追踪 `EffectRes` 到原版 `AttackEffectInfoManager.GetPath()` 等资源解析代码，再检查对应的 Prefab 和依赖。`SteriaBuild/VFXSource/NativeAttackReference/README.md` 记录了本仓库的 UnityPy 导出、索引与覆盖范围。皮肤动作挂点、卡页骰子的 `EffectRes` 和特殊能力主动创建的特效是不同入口，应分别查调用方。

## 六、结果如何用于模组实现

- 将观察到的真实 API 签名用于自有 C# 调用或 Harmony 补丁；不要复制整个反编译类到模组。
- 反编译出的 C# 是工具根据 IL 重建的表示，局部变量名、迭代器、闭包和短路结构可能与原始源码不同。争议点回到 IL、元数据和调用方确认。
- 先用针对实际游戏 `Managed/` 程序集的 API 编译检查确认类型和签名，再做行为级检查。仓库示例见 `SteriaBuild/Verification/ChristashaParticleV2/verify_api.ps1`；Harmony 实战和重载绑定见[Harmony 与 BaseMod 框架](09_Harmony与BaseMod框架.md)。
- 将程序集路径、文件版本、SHA-256、查询类型/方法、关键调用点和验证方式记录在交付材料中。游戏更新后重新核对输入程序集，旧反编译输出和旧签名不自动适用于新版本。
- 不要把 `SteriaBuild/Assembly-CSharp/` 的全量导出、游戏程序集副本或 Unity 原版资源混入模组发布内容；这些本地参考文件已有忽略规则，发布只包含自己编写或获准分发的代码和资源。
