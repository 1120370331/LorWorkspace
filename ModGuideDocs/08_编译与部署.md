# 编译与部署操作手册

## 本仓库已核实的实际游戏目录（2026-09-08）

当前实际使用的游戏从 `D:\Game Center\Steam\steamapps\common\Library Of Ruina` 加载；模组目录为其 `LibraryOfRuina_Data\Mods\SteriaModFolder`。依据是 Player.log 中 Steria Logger 和资源加载的真实路径。

本机还有 C 盘 Steam 安装目录。**仅复制到 C 盘不能视为完成同步。** 部署前先核对运行进程路径或最新 Player.log 的模组加载路径；以实际加载目录为主，并核对 DLL 和本次相关 XML 的 SHA256。仓库模组文件夹的 DLL 也可能被其他部署流程覆盖，发布源应采用本次构建且验证过的输出，不能仅凭同名文件判断版本。

**2026-09-09 补充：** 薇莉亚外观部署时，`Path.resolve()` 核实 C 盘 Steam 的模组入口实际解析到上述 D 盘目录。多条安装路径可能是同一目录的链接别名；应按解析后的真实路径去重备份和写入，再对每个用户入口核对哈希，避免重复覆盖或把第二次覆盖误当成另一份部署。本次只同步相关 PNG、皮肤 XML 与司书书页的单个外观指向，未覆盖无关 DLL 或战斗数据。

## 二、创建C#项目

### 步骤1：新建项目

1. 打开Visual Studio
2. 文件 → 新建 → 项目
3. 选择 **类库 (.NET Framework)**
4. 框架选择 **.NET Framework 4.7.2**
5. 项目名称如 `MyMod`

### 步骤2：项目文件配置 (.csproj)

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net472</TargetFramework>
    <AssemblyName>MyMod</AssemblyName>
    <OutputType>Library</OutputType>
    <LangVersion>latest</LangVersion>
  </PropertyGroup>

  <ItemGroup>
    <!-- 游戏核心引用 -->
    <Reference Include="Assembly-CSharp">
      <HintPath>..\Libs\Assembly-CSharp.dll</HintPath>
      <Private>false</Private>
    </Reference>

    <!-- Harmony库 -->
    <Reference Include="0Harmony">
      <HintPath>..\Libs\0Harmony.dll</HintPath>
      <Private>false</Private>
    </Reference>

    <!-- BaseMod框架 -->
    <Reference Include="BaseMod">
      <HintPath>..\Libs\BaseMod.dll</HintPath>
      <Private>false</Private>
    </Reference>

    <!-- Unity引用 -->
    <Reference Include="UnityEngine.CoreModule">
      <HintPath>..\Libs\UnityEngine.CoreModule.dll</HintPath>
      <Private>false</Private>
    </Reference>
    <Reference Include="UnityEngine">
      <HintPath>..\Libs\UnityEngine.dll</HintPath>
      <Private>false</Private>
    </Reference>
  </ItemGroup>
</Project>
```

## 四、编译方法

### 方法1：Visual Studio编译

1. 打开解决方案 (.sln)
2. 选择 **Release** 配置
3. 生成 → 生成解决方案 (Ctrl+Shift+B)
4. 输出位于 `bin/Release/net472/MyMod.dll`

### 方法2：命令行编译 (dotnet CLI)

```bash
# 进入项目目录
cd YourModProject

# 编译Release版本
dotnet build -c Release

# 输出位置
# bin/Release/net472/MyMod.dll
```

### 方法3：命令行编译 (MSBuild)

```bash
# 使用MSBuild
msbuild MyMod.csproj /p:Configuration=Release

# 或使用Visual Studio Developer Command Prompt
devenv MyMod.sln /build Release
```

### 自动复制脚本 (Post-Build Event)

在项目属性 → 生成事件 → 后期生成事件中添加：

```batch
xcopy /Y "$(TargetPath)" "C:\Program Files (x86)\Steam\steamapps\common\Library Of Ruina\Mods\MyMod\Assemblies\"
```

或在.csproj中添加：

```xml
<Target Name="PostBuild" AfterTargets="PostBuildEvent">
  <Copy SourceFiles="$(TargetPath)"
        DestinationFolder="C:\Path\To\Game\Mods\MyMod\Assemblies\" />
</Target>
```

## 六、调试配置

### 默认方式：优先模拟工程验收，围绕一个主日志分析

**原则：鉴于操作游戏、进入指定接待和重复触发场景比较复杂，日常开发尽量使用模拟工程验收，不把启动游戏或游戏内操作作为默认步骤。** 优先复用已有的托管检查、Unity 模拟场景或原版组件重放，加载当前候选 DLL、XML 与资源，通过可重复输入检查真实接口、结果与画面。只有模拟工程无法覆盖且会影响本次结论的具体问题，才补充有针对性的游戏内验证；未覆盖的完整实战可以明确留待外部验收。

#### 1) 选择能证明本次改动的模拟方式

| 改动 | 优先采用的验收方式 | 需要读取的证据 |
|---|---|---|
| 规则、费用、状态、掉落与阶段 | 引用实际游戏 DLL 和候选模组 DLL 的托管检查 | 触发前后数据、调用结果、次数与边界断言 |
| 卡面、皮肤、图标和投影 | Unity 模拟工程加载实际资源及原版 UI/外观组件 | 尺寸、绑定、层序、朝向、换头与资源查找结果；必要的截图 |
| 贴图/粒子与动作编排 | 按正式调用、挂点、时钟与角色上下文重放 | 时间点、变换、生命周期和代表帧；实际渲染画面 |
| 剧情、语音、音效与配乐 | 模拟加载、推进、跳过、停止、音量和恢复 | 播放事件、当前行/clip、时长、停止次数与混音试听 |

模拟入口尽量执行生产代码和实际游戏类型，不另写一套永远返回预期结果的逻辑。若为了隔离测试跳过平台成就、缩减界面或近似资源，写明替代部分及其影响。`模拟通过`可以作为相应范围的内部验收结论，不写成`游戏实战通过`。

#### 2) 每次运行只认一个明确的主日志文件

- 每次创建独立运行目录，例如 `output/acceptance/<运行编号>/`，主日志固定叫 `acceptance.log`；不同运行不能覆盖旧日志，也不能多个进程同时写同一个文件。
- Unity 使用 `-logFile <主日志绝对路径>`，让本次 Editor 日志与测试入口的 `Debug.Log/LogWarning/LogError` 进入该文件。不要再依赖默认 Editor.log、Player.log 或临时控制台来猜本次结果。
- 普通命令行检查将 stdout 与 stderr 合并到本次主日志，并保留真实退出码。若构建、检查与 Unity 重放分阶段运行，可各自作为独立运行，明确本次正在分析哪一份日志；需要统一报告时汇总结果，不让多个写入者竞争一个日志文件。
- 记录运行编号、源码/候选 DLL 哈希、资源版本、测试入口和场景参数；每个关键检查输出场景名、期望值与实际值。截图、视频、音频或结构化数据可作为附件，其路径写入主日志。
- 用单一最终结果标记结束本次检查，并报告未覆盖项。异常必须包含上下文；成功标记只能在全部必需检查和结果输出完成后写入，不能在初始化成功时提前打印。
- 控制输出量：记录阶段切换、关键事件和失败数据，避免逐帧刷屏。详细诊断可按开关启用，原始日志仍保留以便回查。

新模拟入口可以按下面的内容组织日志；格式为示意，现有入口沿用其真实标记，不凭空声称已输出这些字段：

```text
[ACCEPT] BEGIN run=<编号> candidate=<DLL哈希> entry=<入口>
[CASE] name=PendingBuff_NextRound expected=active:5,ready:0 actual=active:5,ready:0 result=PASS
[ARTIFACT] path=<代表帧或音频路径> purpose=<检查目的>
[COVERAGE] covered=<已验证路径> excluded=<替代部分与未覆盖项>
[ACCEPT] END result=PASS cases=<数量> candidate=<同一DLL哈希>
```

#### 3) 启动模拟工程时显式指定日志

以下以已有的敌方配牌费用检查为例。先按[检查说明](../SteriaBuild/Verification/EnemyPatternCardCost/README.md)完成候选构建、检查程序编译和 `prepare_ui.py`，再从仓库根目录执行。该示例不启动游戏：

```powershell
$acceptanceRunId = (Get-Date -Format 'yyyyMMdd-HHmmss') + '-' + [guid]::NewGuid().ToString('N')
$acceptanceRunDir = Join-Path (Join-Path (Get-Location).Path 'output/acceptance') $acceptanceRunId
New-Item -ItemType Directory -Path $acceptanceRunDir | Out-Null
$acceptanceLog = Join-Path $acceptanceRunDir 'acceptance.log'
$acceptanceProject = (Resolve-Path 'output/enemy-pattern-cost/UnityProject').Path
$acceptanceArgs = @(
    '-batchmode',
    '-projectPath', ('"' + $acceptanceProject + '"'),
    '-executeMethod', 'EnemyPatternCostEntry.Run',
    '-logFile', ('"' + $acceptanceLog + '"')
)
$acceptanceProcess = Start-Process 'C:/Program Files/Unity/Editor/Unity.exe' `
    -ArgumentList $acceptanceArgs -WindowStyle Hidden -PassThru
$null = $acceptanceProcess.Handle
"PID=$($acceptanceProcess.Id) LOG=$acceptanceLog"
```

先确认进程实际使用的项目与日志路径。一个 Unity 工程只允许一个 Editor 使用；上一轮未退出时先查清它是否仍在检查或已卡在清理，避免不断启动新实例争用工程。需要结束卡住的模拟进程时，先确认 PID 和命令行属于本次任务，不关闭用户的其他编辑器或游戏。

#### 4) 主动读取日志，按输出定位问题

在同一 PowerShell 会话中检查上述运行；进程尚未结束时分次读取，不长时间阻塞等待：

```powershell
if (Test-Path -LiteralPath $acceptanceLog) {
    Get-Content -LiteralPath $acceptanceLog -Tail 100
    Select-String -LiteralPath $acceptanceLog `
        -Pattern 'ENEMY_PATTERN_NATIVE_UI_PASS','FAIL','Exception','error','Fatal'
}
if ($acceptanceProcess.HasExited) {
    $acceptanceProcess.WaitForExit()
    "ExitCode=$($acceptanceProcess.ExitCode)"
} else {
    "RUNNING: PID=$($acceptanceProcess.Id)"
}
```

关键词搜索用于定位，结论应读取前后文：堆栈中的方法签名也可能带 `Exception`，一条历史 PASS 也可能来自错误候选。主日志不存在、仍停在许可证/导入阶段、出现工程锁、缺入口、DLL 加载失败或没有最终标记，都不能算检查通过。

正常结束后同时核对：**本次候选正确、必需场景结果完整、无未处理失败、最终标记存在、进程成功退出**。上面费用检查的真实标记是 `ENEMY_PATTERN_NATIVE_UI_PASS`，其覆盖范围只到原版卡面费用绑定，不能扩展为整场战斗已验收。

失败时从第一处有意义的错误向前后追踪：区分环境/夹具问题和产品问题，修最小相关范围；修复后使用新运行目录，只重跑受影响检查。若一个检查始终需要模拟工程尚未具备的系统，再说明缺口并决定是否做特定游戏内验证。

**验收结果应写清：** 使用哪个模拟工程、加载哪个候选、主日志在哪、哪些场景通过、哪些被替代或未覆盖。美术和听感仍需查看日志指向的真实渲染或音频附件，不能仅凭自动断言宣称好看或好听。

### 游戏内调试：仅在具体问题需要时使用

模拟工程无法复现的加载、完整场景交互或兼容问题，可使用下列调试方式。它不作为每次改动的默认验收步骤。

1. 启动游戏
2. Visual Studio → 调试 → 附加到进程
3. 选择 `LibraryOfRuina.exe`
4. 设置断点进行调试

### 启用调试日志

```csharp
using UnityEngine;

public class MyMod
{
    public static void Log(string message)
    {
        Debug.Log($"[MyMod] {message}");

```

## 七、常见编译错误

### 错误1：找不到类型或命名空间

```
error CS0246: 找不到类型或命名空间名"BattleUnitModel"
```

**解决：** 添加Assembly-CSharp.dll引用

### 错误2：程序集版本冲突

```
warning CS1701: 假定程序集引用与标识匹配
```

**解决：** 确保使用与游戏版本匹配的DLL

### 错误3：目标框架不匹配

```
error : 项目的目标框架版本高于引用的程序集
```

**解决：** 将目标框架改为.NET Framework 4.7.2

### 错误4：Harmony方法签名错误

```
error CS0115: 没有找到适合的方法来重写
```

**解决：** 检查方法签名是否与基类一致
