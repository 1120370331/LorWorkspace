# 核心书页与被动系统操作手册

**同一骰子的追加投掷：** 先把规则触发范围写清：仅拼点胜利，还是单方面攻击命中也算。原生 `DiceCardAbility_repeat3.ActivateBonusAttackDice()` 把当前 `BattleDiceBehavior.isBonusAttack` 置为 `true`，拼点和单方面攻击调度器据此保留当前骰再投；`playingCard.AddDiceFront` 则把复制骰排到下一骰，语义不同。以 AceTaffy 的“第三颗攻击骰、每幕一次、消耗压力”为例，拼点胜利用 `OnWinParrying`，单方面命中用 `OnSucceedAttack` 且确认 `behavior.TargetDice == null`（该骰经 `BeforeRollDice(null)`）；拼点胜利后的 `SuccessAtk` 也可能触发，不能只凭命中回调当作单方面攻击。两个入口共用 `TryRepeat` 的骰位/类型、禁用标志、资源余量、每幕 latch 和扣压逻辑，在真正满足条件时才消费并设置 `isBonusAttack`，避免双触发或错时扣资源。验收分别走拼点与单方面的真实派发、同一骰的第二次 `RollDice` 和 `NextDice` 边界，并覆盖命中后再进入拼点回调、同幕第二张页、资源不足及混入防御骰；复制一个布尔值或只测辅助函数都不能宣称全场景成立。对应候选见 `AceTaffy/src/TaffyPassives.cs` 和 `AceTaffy/Verification/MechanicsProbe.cs`，模拟覆盖仍需按其实测边界报告。

## 二、核心书页属性详解

### 抗性值 (Resist)

| 值 | 说明 | 伤害倍率 |
|----|------|----------|
| `Weak` | 脆弱 | 2.0x |
| `Normal` | 普通 | 1.0x |
| `Endure` | 耐性 | 0.5x |
| `Immune` | 免疫 | 0x |
| `Fatal` | 致命 | 3.0x |

### 抗性类型

| 标签 | 说明 |
|------|------|
| `SResist` | 斩击HP抗性 |
| `PResist` | 穿刺HP抗性 |
| `HResist` | 打击HP抗性 |
| `SBResist` | 斩击混乱抗性 |
| `PBResist` | 穿刺混乱抗性 |
| `HBResist` | 打击混乱抗性 |

### 被动引用方式

```xml
<!-- 引用模组内被动（使用模组内ID） -->
<Passive>9000001</Passive>

<!-- 引用原版被动（使用@origin前缀） -->
<Passive Pid="@origin">10008</Passive>

<!-- 引用原版专属书页 -->
<OnlyCard Pid="@origin">602001</OnlyCard>
```

### 核心书页选项

```xml
<!-- 多卡组支持 -->
<Option>MultiDeck</Option>

<!-- 远近混合类型 -->
<RangeType>Hybrid</RangeType>

<!-- 分类 -->
<Category>TheIndex</Category>
<Category>Thumb</Category>
```

  <Passive ID="9000003">

## 四、被动类型说明

### 可转移被动
- 默认情况，可以通过燃烧书页转移给其他角色
- 不需要特殊标签

### 不可转移被动
```xml
<CanGivePassive>false</CanGivePassive>
```
- 无法通过燃烧转移
- 通常用于角色专属机制

### 固有被动 (InnerType)
```xml
<InnerType>10000302</InnerType>
```
- 同一InnerType的被动互斥
- 用于实现"升级"或"替换"机制
- 例如：基础版和强化版被动使用相同InnerType

## 五、C#被动能力实现

### PassiveAbilityBase 常用方法

```csharp
public class PassiveAbility_MyMod_Example : PassiveAbilityBase
{
    // === 回合/幕相关 ===

    // 每一幕开始时
    public override void OnRoundStart()
    {
        owner.bufListDetail.AddKeywordBufThisRoundByEtc(KeywordBuf.Strength, 1, owner);
    }

    // 每一幕结束时
    public override void OnRoundEnd()
    {
        // 幕结束效果
    }

    // 战斗开始时（整场战斗）
    public override void OnWaveStart()
    {
        // 开场效果
    }

    // === 骰子相关 ===

    // 投骰前（可修改骰子）
    public override void BeforeRollDice(BattleDiceBehavior behavior)
    {
        // 检查是否为攻击骰子
        if (IsAttackDice(behavior.Detail))
        {
            behavior.ApplyDiceStatBonus(new DiceStatBonus { power = 1 });
        }
    }

    // 投骰后
    public override void OnRollDice(BattleDiceBehavior behavior)
    {
        // 投骰后效果
    }

    // 造成伤害前
    public override void BeforeGiveDamage(BattleDiceBehavior behavior)
    {
        // 伤害前效果
    }

    // === 拼点相关 ===

    // 拼点胜利
    public override void OnWinParrying(BattleDiceBehavior behavior)
    {
        owner.cardSlotDetail.RecoverPlayPoint(1);
    }

    // 拼点失败
    public override void OnLoseParrying(BattleDiceBehavior behavior)
    {
        // 拼点失败效果
    }

    // 攻击成功
    public override void OnSucceedAttack(BattleDiceBehavior behavior)
    {
        // 攻击成功效果
    }

    // === 受伤相关 ===

    // 受到伤害前（返回true则无效化伤害）
    public override bool BeforeTakeDamage(BattleUnitModel attacker, int dmg)
    {
        return false; // 返回true无效化伤害
    }

    // 受到伤害后
    public override void AfterTakeDamage(BattleUnitModel attacker, int dmg)
    {
        // 受伤后效果
    }

    // 伤害减免
    public override int GetDamageReductionAll()
    {
        return 2; // 所有伤害-2
    }

    // === 死亡相关 ===

    // 自身死亡时
    public override void OnDie()
    {
        // 死亡效果
    }

    // 其他单位死亡时
    public override void OnDieOtherUnit(BattleUnitModel unit)
    {
        if (unit.faction != owner.faction) // 敌人死亡
        {
            owner.bufListDetail.AddKeywordBufByEtc(KeywordBuf.Strength, 1, owner);
        }
    }

    // 击杀目标时
    public override void OnKill(BattleUnitModel target)
    {
        owner.RecoverHP(10);
    }

    // === 属性修改 ===

    // 速度骰子数量加成
    public override int SpeedDiceNumAdder()
    {
        return 1; // +1速度骰
    }

    // 速度骰子结果加成
    public override int GetSpeedDiceAdder(int speedDiceResult)
    {
        return 1; // 速度+1
    }

    // 最大HP加成
    public override int GetMaxHpBonus()
    {
        return 20;
    }

    // 最大光芒加成
    public override int MaxPlayPointAdder()
    {
        return 1;
    }

    // === 免疫相关 ===

    // 免疫特定Buff
    public override bool IsImmune(KeywordBuf buf)
    {
        return buf == KeywordBuf.Binding; // 免疫束缚
    }

    // 是否无敌
    public override bool isInvincible => false;

    // 是否不朽（HP不会降到0）
    public override bool isImmortal => false;
}
```

## 六、变幻莫测（变化莫测）：逐幕配牌与节奏安排

这里讨论的是敌方被动“每幕将意图使用的书页置入手中，光芒消耗为 0”的制作方式。本仓库名称为“变幻莫测”。它通过每幕配牌组织敌方行动；具体采用固定轮换、条件分支还是随机抽取，要看对应实现。

### 怎么实现

**做什么：** 先定义每种模式给哪些书页，再用序列表决定本幕使用哪个模式。典型流程如下：

```text
Init / OnWaveStart：重置本单位幕计数
OnRoundStart：
  按幕计数读取开场序列；开场结束后对循环序列取模
  取得该模式的基础书页，以及情感/阶段条件满足时的追加书页
  按设计清理旧牌，再逐张 AddTempCard(new LorId(包ID, 书页ID))
  对成功创建的实例 EnemyPatternCardCost.MakeFree(card)、SetPriorityAdder(优先级)
  推进本单位幕计数
```

- **配牌与循环分开。** `patterns` 保存书页组合，`initialSequence` 只执行一次，`loopSequence` 重复执行。序列表填模式索引，不能把书页 ID 当成模式编号。
- **计数边界写清。** 本仓库常见实现按 Wave 重置；如果要跨 Wave 延续或变身时重新开场，另行保存或重置状态。混乱、眩晕时是否仍推进序列也应明确，避免关键幕被跳过却不符合设计。
- **先确认是否完全接管牌库。** `ExhaustAllCards()` 会清空预留、使用中、手牌、弃牌与牌库，不能理解为“只清手牌”。保留正常抽牌或特殊持久牌的设计应使用对应的局部清理方案。
- **检查加牌结果。** `AddTempCard` 可能因书页不存在、入手条件或手牌上限返回 null；记录失败，不把“尝试加入”当成已配齐。它会创建临时、佚亡实例。实际免耗光与卡面费用显示分开处理，不应改共享 XML 费用。
- **免耗光不等于卡面显示 0。** 本模组的敌方配牌使用 `EnemyPatternCardCost.MakeFree(card)`：内部仍保留 `SetCostToZero(true)` 供选牌和耗光结算使用，同时只为该敌方书页实例登记显示标记。`BattleDiceCardUI.SetCard` 显示原始费用并沿用正常费用样式；普通降费、玩家书页与其他模组不受此标记影响。仅调用 `SetCostToZero(true)` 会让卡面也显示降费后的 0。
- **优先级不是强制播放顺序。** 实际选牌还受 XML Priority、PriorityScript、单位修正、可用速度骰与卡牌限制影响。严格的选牌/选目标需求还需对应 AI；攻击演出先后另由战斗规则决定。
- **明确装备范围。** 挂到需要接管出牌的敌方核心书页；玩家奖励版是否保留这项能力单独设计，避免司书装备后意外清空自组卡组。

**为什么：** 敌方每幕都有明确行动组合，才能把机制节奏做成玩家可以观察和应对的过程；仅改变形态或加一个幕计数，并不会自动安排出牌。

**带来什么效果：** 敌人能稳定呈现指定策略，配牌、情感强化与阶段变化可以分别修改和核对。

### 每幕怎么安排

先定每种模式的战术职责，再填具体书页。下面是设计模板，数值和循环长度按接待强度调整：

| 模式 | 配牌方向 | 玩家应能观察或应对什么 |
|---|---|---|
| 资源/铺垫 | 建立状态、资源或后续联动，保留普通攻击 | 看懂机制正在准备，选择打断或积累资源 |
| 常态压力 | 主攻击配防御、辅助或连携 | 需要拼点和分配目标，但仍有应对空间 |
| 爆发/关键机制 | 加入群攻、特殊书页或阶段核心牌 | 在此前有线索的前提下，检验玩家准备与防御 |
| 缓冲/重整 | 降低关键威胁，恢复或重新建立资源 | 给玩家回光、抽牌、调整和反击的机会 |

开场序列适合依次介绍机制；循环序列负责后续压力起伏。不要因敌方零费就把每幕都填满最高威胁书页。逐幕核对“手牌数量、实际可用速度骰、手牌上限、关键牌优先级”，尤其是情感等级提升后的追加牌；牌已进手不代表本幕一定会使用。依赖前置资源的爆发牌，还要核对资源取得与消耗的实际时点。

### 以现有模组为例

- [斯拉泽雅 PassiveAbility_9002006](../SteriaBuild/SlazeyaAbilities.cs)：前 4 幕按模式 **1→2→3→4**，之后循环 **2→3→1→3→4**；每模式基础 4 张，情感等级达到 3 后追加对应 2 张。实例优先级从 100 起逐张递减 10。文件顶部仍有旧循环注释，当前应以 `_initialSequence`、`_loopSequence` 和 `_patterns` 的实际数组为准。
- [克丽丝塔夏 PassiveAbility_9009007](../SteriaBuild/ChristashaAbilities.cs)：开场模式 **1→2→3→4→5→6**，之后循环 **2→3→5→1→4→6**；基础每模式 6 张，情感强化另有追加，其中“汐火联星”分支加入两份实例。两份入手是否都能打出，仍需核对可用速度骰与 AI。
- [荆棘幻影 PassiveAbility_9005006](../SteriaBuild/VeliaEgoBossAbilities.cs)：按速度骰数量抽牌，再把当前手牌设为零费，没有上述固定模式表。同名被动不代表同一套出牌算法。

### 最小检查

从第一幕走过开场末幕、循环第一幕和一次循环回绕，核对实际手牌与选牌；再检查情感门槛前后、混乱/眩晕和重新进入 Wave。记录幕号、模式、加牌失败与实际使用的书页，确认压力节奏符合预期。原生相关 API 可查 `BattleAllyCardDetail.AddTempCard/ExhaustAllCards` 与 `BattleDiceCardModel.GetPriority`；这不是一份所有原版同名被动都共用的算法。
