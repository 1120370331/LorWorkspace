# 00：一个优秀的《废墟图书馆》模组包含什么

一个优秀的模组，让玩家能顺利进入接待、理解敌人的规则、通过构筑与战术应对挑战，战后获得值得使用的书页，也记住其中的角色与故事。机制、画面、声音和演出应围绕同一个主题合作。

本章是整套教程的起点。先用三层结构决定“要做哪些内容、为什么做、做到什么程度”，再进入各章学习具体配置和实现。以下以包含新角色与接待的模组为主要场景；纯书页包、皮肤包等按自己的范围选取相关内容。

| 层级 | 主要目标 | 玩家应得到的体验 |
|---|---|---|
| **基础层** | 规则与接待流程完整，能进入、能打完、能获得并使用奖励 | “我知道怎么玩，这场战斗有明确规则和应对方法。” |
| **优化层** | 给已有内容补齐身份、叙事与视听反馈 | “我能认出这些角色，理解他们为何而战，也能看清每次行动。” |
| **卓越层** | 深入改造原版玩法，并把关键机制、情绪与视听组织成完整体验 | “熟悉的系统有了新的选择，这场战斗也留下了值得记住的瞬间。” |

这三层是制作顺序与投入重点。粒子、配音和镜头按表现需要选用；高完成度也可以来自精炼的机制、准确的贴图和克制的演出。所有层级都要满足规则正确、可读、稳定和可复现。

## 默认验收方式：模拟工程优先，读取明确的主日志

鉴于启动游戏、操作界面和重复进入指定战斗的成本较高，**尽量使用模拟工程验收，不把游戏内操作作为每次改动的默认步骤**。优先在托管检查或 Unity 模拟工程中加载当前生产 DLL、XML、资源和必要原版组件，按可重复输入验证规则、UI、动作、剧情与声音。

每次运行使用一个明确的主日志文件，例如独立运行目录下的 `acceptance.log`；记录候选、场景、期望/实际结果与最终结论，主动读取日志分析。渲染帧和试听文件可以作为日志指向的附件。不要只看到程序启动或一句 PASS 就宣称完成，也不要把不同运行和候选的日志混在一起。

本章后文的“实际路径”“真实角色上下文”描述需要覆盖的行为与数据，优先在模拟工程中复现。模拟未覆盖的部分如实标记；只有具体缺口影响本次验收结论时，才安排针对性的游戏内检查。详见[08_编译与部署：模拟工程与日志验收](08_编译与部署.md)。

## 一、先写清模组想带给玩家什么

### 做什么

在建 XML 和画第一张图之前，先回答五个问题：

1. **主题是什么？** 这批角色的组织、冲突、价值观和战斗方式有什么联系？
2. **面向哪个进度？** 玩家到什么阶段挑战，预计掌握哪些原版资源？
3. **核心选择是什么？** 玩家需要管理什么资源、判断什么时机、付出什么代价？
4. **角色为什么这样战斗？** 武器、被动、书页与人物经历如何相互解释？
5. **打完留下什么？** 玩家带走什么核心书页、战斗书页、构筑思路或故事信息？

可以先写一句项目描述，例如：“一场围绕保护同伴与积累反击机会的接待，玩家需要识别敌方守护关系，战后能得到以保护换取反攻的构筑。”这是设计示意，不是必须采用的题材。

### 为什么

明确体验目标后，才能判断该增加一个机制、补一段剧情，还是打磨某次攻击。没有目标时，容易出现卡牌、角色和特效各有风格，却互相解释不了的情况。

### 带来什么效果

后续每项工作都能回答“它帮助玩家理解、选择或感受什么”，并据此确定优先级。

## 二、基础层：把接待和奖励做完整

### 需要包含什么

| 内容 | 做什么 | 为什么，以及带来什么效果 |
|---|---|---|
| 模组入口与依赖 | 配置模组标识、数据入口、程序集、所需框架、资源路径与本地化 | 游戏能加载正确版本，玩家知道安装条件；不同模组的 ID 和脚本不会意外冲突 |
| 司书核心书页 | 定义生命、混乱抗性、速度、抗性、被动、装备条件和专属书页关系 | 奖励有明确战斗定位，装备后能形成可用构筑 |
| 敌方核心书页 | 定义敌方实际需要的属性、被动与阶段能力 | 敌人按接待设计运作；敌方特殊规则与玩家得到的奖励版本分别考虑 |
| 战斗书页 | 设计费用、距离、使用效果、抽牌/回光、消耗与专属限制 | 卡组有资源循环，每张牌有使用时机与取舍 |
| 骰子 | 配置顺序、点数、斩/打/突/防/闪、反击、动作及命中/拼点效果 | 书页规则落实到真实交锋，描述与结算一致 |
| 被动与状态 | 确定触发时机、层数、持续时间、清理条件、归属与转移限制 | 角色特色可被理解和利用，效果不会串单位或跨幕残留 |
| 敌方单位 | 把敌方核心书页、卡组、名称、外观、属性和掉落等关联起来 | 实际出现的敌人与设计一致，不只是配置文件中存在一张书页 |
| 敌方用牌与行为 | 配置资源供给、选牌逻辑、目标选择、行动循环和必要的阶段状态 | 敌人能使用设计好的机制，玩家能观察规律并应对 |
| 接待编排与出战单位 | 确定每个 Wave 的敌人组合、位置、增援、可用楼层/人数、胜负与阶段条件 | 单个单位形成有节奏的战斗；“单位定义”与“在哪场、哪波出场”分别管理 |
| 接待条件 | 配置邀请所需书籍、前置关卡或其他已实现的入口条件 | 玩家能在预期进度发现并进入接待，条件不会互相锁死 |
| 奖励与获取 | 接通敌人掉落、可获得的书、烧书结果、核心书页与战斗书页获取路径 | 玩家打赢后真正拿到承诺的奖励，并能在书库里找到与使用 |
| 基础说明与平衡 | 补齐名称、规则、关键词；对照目标进度检查威力、费用、抗性与资源循环 | 玩家能根据规则做决定，胜负有可解释性，奖励不会因漏配而无法使用 |

敌方需要按幕展示特定策略时，可使用“变幻莫测”式配牌：预设模式、开场与循环序列，再安排铺垫、压力、爆发和缓冲。具体实现与配牌安排见[03 第六节](03_核心书页与被动系统.md#六变幻莫测变化莫测逐幕配牌与节奏安排)。

“接待单位”可以从编排角度理解：本场安排谁出场、如何组合、何时增援。敌方单位定义则回答这个单位自身是谁、装备什么、用什么卡组。两者都要落实，不能只完成其中一边。

异想体书页、E.G.O、额外资源条或新的骰子类型在主题需要时加入。它们一旦影响玩法，其规则、说明与正确结算就属于基础层责任。实现章节见[05_异想体书页系统](05_异想体书页系统.md)。

### 基础层怎样算完成

优先用模拟工程按下面的玩家路径执行生产接口，检查每一步的输入、结果和关联；尚不能模拟的节点注明缺口：

```mermaid
flowchart LR
    A[满足接待条件] --> B[进入正确关卡与Wave]
    B --> C[敌人按设计行动]
    C --> D[玩家理解并应对机制]
    D --> E[胜负结算与掉落]
    E --> F[烧书或约定获取方式]
    F --> G[找到并装备核心书页和卡组]
    G --> H[奖励在下一场战斗中正常使用]
```

同时检查失败、重试和退出：不会卡住结算，不会留下上一场的状态。难度按预期进度与代表性构筑评估；如果某机制需要识别弱点或准备防御，应给予足够信息和应对机会。

**进入优化层前应能说明：** 接待入口在哪里，敌人怎样打，玩家怎样赢，奖励怎样获得，装备后怎样发挥作用。最终美术尚未完成时可以先用可用资源验证流程，但正式版本应消除错误引用与无意占位。

## 三、优化层：让角色有身份，让行动和故事可读

### 需要包含什么

| 内容 | 做什么 | 为什么，以及带来什么效果 |
|---|---|---|
| 接待图标 | 为组织或接待设计易辨识的标志，统一轮廓、留白与高亮状态，并核对接待入口的图标绑定 | 玩家在选择接待时能识别来宾所属与主题，入口呈现与内容一致 |
| 书籍图标 | 为掉落书籍和需要自定义图标的核心书页设计标志，确定与接待图标共用还是采用变体，并核对各自 BookIcon | 玩家在奖励、书库和烧书界面能识别来源，接待与奖励形成连续的视觉身份 |
| 战斗书页卡图 | 绘制横向 **4:3** 的故事性插画，一眼读出角色、动作和事件，细看读到位置、背景与细节，镜头有特色和动态；可手绘、委托或用绘图 AI 生成，教程以 AI 直接生成为例，Codex 中使用 imagegen 调用 | 小尺寸下仍能读出主题，同系列统一又能区分各张书页 |
| 核心书页皮肤 | 按[原版实测模板](12_战斗单位分层建模与核心书页投影.md#原版比例与模板约束)锁定头身及长宽比例，再制作头部、表情与身体姿势，处理头领拼接、武器、遮挡、大小、方向、底盘和司书投影 | 玩家能认出角色，装备奖励后外观正确；动作中比例稳定、头身不脱节 |
| 战斗贴图特效 | 按斩、打、突、防、远程等职责设计前锋、主体、拖尾和消散，并绑定正确动作与书页 | 玩家看得清出手方向、力量与材质；主题在战斗中延续 |
| 动作与基础打击反馈 | 配合准备、出手、接触、收势安排姿势与音效，不误报失败或未命中 | 行动有因果和重量，视觉与实际结算一致 |
| 战前剧情 | 交代来宾、来意和冲突，让玩家知道为什么接待 | 开始战斗前形成期待，理解人物立场 |
| 战中剧情 | 在阶段变化或关键选择处补充信息，并控制次数、跳过与恢复 | 机制变化有动机，剧情不会让战斗卡住或反复打断 |
| 战后剧情 | 回应冲突与结果，连接奖励及后续发展 | 接待有收束，玩家理解自己经历了什么 |
| 战斗对话与事件语音 | 制作开幕、击杀、死亡、同伴死亡、胜利与特殊台词；需要配音时绑定同一次选句 | 人物在行动中显出性格，多人同时触发也不会错配或重叠轰鸣 |
| 动作音效与环境声 | 区分挥动、接触、技能提示和环境，统一音量、材质与触发时点 | 声音帮助玩家识别动作，避免全靠高亮和震屏传递反馈 |
| 核心书页剧情与书籍故事 | 补充获得书页后可阅读的人物经历、视角或主题，并核对书页/故事关联与本地化 | 奖励成为了解角色的入口，战后阅读与战斗印象互相补充 |
| 场景、图标与信息呈现 | 统一地图氛围、关键状态图标、词条说明、可读字号与遮挡关系 | 自定义机制容易理解，角色、卡图和战场处于同一美术体系 |

**核心书页剧情是什么：** 它是玩家在书页/书籍阅读界面查看的人物文字，和战前战后的完整剧情界面分开制作，也和被动规则描述分开。人物经历可以解释能力来源，但关键战斗规则仍要出现在玩家作决策时能看到的位置。

本仓库可查阅 [BookStory.xml](../SteriaBuild/SteriaModFolder/Data/BookStory.xml)了解已有的人物故事材料，再核对本项目的 BookDesc、BookID、本地化与加载入口。该文件可作内容参考，关联是否成功以实际阅读界面为准；不要只因 XML 中有文字就认为已展示。

### 怎样把这些内容做成同一个角色

先确定角色的行动方式和情绪，再让各类资源分别表达它。例如同一“保护同伴”的主题，可以由核心书页被动表达资源取舍，卡图表现挡在危险前的瞬间，身体姿势表现守势，特效强调接触区域，音效突出承压，对话表达动机，书页故事说明这种选择的来历。

这些内容不必逐字重复。卡图提供一个瞬间，战中对白给出当下反应，核心书页剧情留下更完整的个人视角；它们共同增加对角色的理解。

### 优化层怎样算完成

- 在接待入口、奖励、书库和烧书界面检查接待/书籍图标，确认绑定正确、缩小时可辨认、普通与高亮状态一致。
- 在实际卡框与手牌大小下一眼认出角色、动作和事件；放大后能读到位置、背景与叙事细节，镜头选择具有动态和画面感。
- 在敌我两侧、不同动作与司书投影中检查皮肤比例、头部、武器与接地。
- 在真实角色上下文里检查贴图特效的大小、挂点、朝向、透明边和退场，不能只看孤立母图。
- 读完并跳过剧情各一次，确认战斗、BGM 和 UI 恢复；台词与录音同句、音量设置生效。
- 实际打开核心书页/书籍故事，确认是正确角色的内容，文字完整可读。

**这一层的结果：** 玩法已经成立，角色身份和行动反馈又能被玩家清楚感受到。

## 四、卓越层：拓展原版玩法，组织完整演出

### 需要考虑什么

| 内容 | 做什么 | 为什么，以及带来什么效果 |
|---|---|---|
| 粒子特效 | 按主锋、体积、副迹、碎屑、烟雾等职责组合运动、材质与寿命；参考原版真实播放而非只取纹理 | 获得随时间和空间变化的表现，重点动作更丰富且保持可读 |
| 演出编排 | 将姿势、位移、效果、结算反馈、音效、对白与恢复组织到同一事件顺序 | 准备建立期待，接触形成重音，收势给玩家消化结果 |
| 视角与镜头 | 为必要时刻设计取景、跟随、推拉、短暂镜头强调及恢复 | 引导玩家注意正确对象，同时保留交战关系和重要 UI |
| 高光时刻 | 选择少量有机制或剧情依据的阶段转变、关键防御、终结技或结局行动 | 高潮有铺垫和回落，玩家能记住角色做了什么 |
| 视觉重音与光照 | 用局部亮锋、短闪、颜色变化或适度辉光突出焦点 | 提高关键瞬间的辨识度，不让持续满屏高亮吞掉轮廓 |
| 配乐与音乐变化 | 设计常态、紧张、阶段变化和结局的音乐关系，处理衔接、循环、音量与恢复 | 情绪随战斗发展，配乐给高光和叙事提供节奏 |
| 原版机制重写 | 根据设计目标调整或重写原版资源循环、情感成长、状态交互、拼点或结算规则，明确局部或全局生效范围 | 为熟悉的战斗体系增加新的决策与构筑空间，让玩法变化有完整规则支撑 |
| 原版书页与被动重构 | 重新设计已有核心书页、战斗书页和被动的定位、代价、联动与获取节奏 | 让原本缺少选择空间的内容形成新的使用方式，并与目标进度匹配 |
| 异想体书页与楼层体系改造 | 新增或重做异想体书页，调整效果、代价、选取条件、楼层联动及必要的 E.G.O 配合 | 让情感升级和楼层选择成为更有主题、更有取舍的构筑过程 |
| 跨场景的一致性 | 将角色主题贯穿卡图、皮肤、攻击、剧情、声音和奖励 | 玩家从多个入口感受到同一人物与主题，形成完整印象 |

粒子并不自动比贴图更优秀。选择取决于所需形态、运动与维护成本；贴图可以完成明确的攻击轮廓，粒子可以补充独立运动的碎屑或空间层次。组合后每层都应有可辨认的职责。

“高光”同时包括值得记住的剧情/战斗时刻，以及服务它的视觉强调。稀有书页不必每次都启动最长演出；普通攻击保持流畅，重要动作才有足够对比。

### 原版修改怎样形成有价值的玩法扩展

**做什么：** 先说明原规则存在什么设计问题、希望增加什么选择，再沿实际调用链确定修改点。可以扩展已有能力、替换特定书页效果，也可以重新组织一整套规则；数据扩展、能力脚本和 Harmony 接入方式应按需要选择。

1. **写出修改前后的一次具体决策。** 例如某张原版异想体书页重做后，玩家在获得即时收益和保留后续机会之间需要取舍；不要只写“加强原版”或“重做情感”。
2. **确定范围。** 明确影响指定书页、某个楼层、本模组接待还是所有战斗；记录对应 ID、触发条件与所需前置。全局修改应在模组说明中直接告知玩家。
3. **把规则改完整。** 效果、费用、叠加、触发与清理、选取条件、名称和描述一起核对。异想体书页还要检查实际选取界面、情感阶段、适用单位及与现有楼层能力的组合。
4. **保留可理解的因果。** 机制变化要能从说明和反馈中学会；若改变伤害、拼点或资源规则，相关 UI 和日志应能解释实际结果。
5. **检查组合与边界。** 验证改动生效的场景，也验证不在范围内的原版内容；检查与本项目既有补丁、常用构筑的交互，以及重试、换 Wave、载入后的状态。

**为什么：** 原版机制通常被多个单位、书页和关卡共用。只改一个效果而遗漏选取、描述或生命周期，会让新玩法难以理解，甚至让其他战斗产生意外变化。

**带来什么效果：** 玩家在熟悉的系统中获得新的战术选择，原版内容和模组内容能共同组成明确、连贯的玩法。卓越体现在新选择、主题与整体完成度，改动规模按目标确定。

这里的异想体改造强调对原版效果、选取和楼层联动的深入设计；前面基础层提到的异想体内容，则要求选定方案能正确加载和结算。若机制重写是模组的核心卖点，应在基础原型阶段就实现并验证，不等到美术和演出完成后再接入。

### 演出怎样一步一步安排

先为一个代表性动作写时序表，再扩大到其他动作。下表是职责模板，时长按实际书页和游戏事件确定：

| 阶段 | 做什么 | 玩家读到什么 | 必须守住的关系 |
|---|---|---|---|
| 预告/准备 | 姿势收紧、声音或环境变化，必要时展示台词 | “接下来有重要行动” | 预告不能遮住玩家需要判断的规则 |
| 出手 | 动作、位移与主效果开始，镜头按需要引导 | “谁向哪里行动” | 跟随真实动作挂点和双方朝向 |
| 接触/释放 | 在实际事件处给出主要声画重音 | “力量落在这里” | 不在拼点失败或未命中时伪造确认命中 |
| 余波/收势 | 副迹、碎屑、声音尾部退去，展示实际结果 | “行动结束，结果可读” | 效果寿命与伤害判定分别管理，不为拖尾重复结算 |
| 恢复 | 镜头、场景、音量和临时状态回到应有位置 | “可以继续决策” | 正常结束、取消、跳过与退出都能清理 |

镜头与配乐是共享资源。一次演出接管它们之前，应记录需要恢复的状态；多个角色或效果同时请求时，要有明确先后和退出责任。只恢复坐标而遗漏缩放、只停止音频而不恢复 BGM，都可能污染后续战斗。

### 配乐怎样服务战斗

先确定曲目或音乐层的用途：平稳交锋、压力积累、阶段突破、胜利收束。再明确切换条件、是否从头播放、循环点、淡入淡出与音量。长剧情结束后，应恢复本场此时应有的音乐，避免把上一阶段或上一接待的 BGM 带回来。

音乐、语音和攻击音效要能同时听清。优先在模拟工程中重建战场混音，检查密集攻击与多人说话；不要只分别播放单个文件。来源许可、制作版本和最终发布文件也应可追溯。

### 卓越层怎样算完成

对于原版修改，要能展示修改前后的实际决策差异，并确认选取、效果、说明、奖励与进度相互匹配。局部改动在边界外维持既定行为，全局改动按声明范围生效；异想体书页必须从真实选取到战斗触发完整走通。

优先在模拟工程中完整播放并检查演出，读取日志和渲染/音频附件：开始有信息、主段有焦点、结束有回落；两侧角色、不同目标位置和必要的群攻场景仍成立。镜头不把目标或关键 UI 带出画面，闪光与震屏可控；暂停、跳过、退出和重试后状态正常。

同时确认运行成本：透明覆盖、纹理、粒子峰值、缓存、实例销毁与首播加载不会破坏战斗节奏。性能与稳定性从第一层就需要关注，复杂演出只是增加了需要检查的对象。

## 五、推荐制作顺序：先完成一条完整体验

| 步骤 | 做什么 | 为什么 | 完成后得到什么 |
|---|---|---|---|
| 1 | 确定主题、玩家进度、核心决策和奖励定位 | 为范围与平衡建立共同依据 | 一份简短且可检查的设计目标 |
| 2 | 做一个代表性敌人、一套能循环的卡组和一场接待；核心方案涉及原版机制重写时一并验证 | 尽早发现资源、用牌、结算与共享规则交互问题 | 可从入口打到结算的基础版本 |
| 3 | 接通奖励，并用奖励打一场战斗 | 验证玩家实际获得的内容 | 从挑战到构筑的完整流程 |
| 4 | 打磨代表性角色的卡图、皮肤、贴图特效和声音 | 建立可复用的风格与制作方法 | 一段有明确身份和反馈的战斗 |
| 5 | 补齐剧情、对话和核心书页故事，再扩展其余内容 | 使人物、机制与奖励互相解释 | 内容完整、风格一致的候选版本 |
| 6 | 选择最值得强调的时刻，加入粒子、编排、镜头或音乐变化 | 把精力集中在体验收益最大的地方 | 有铺垫、有高潮、能恢复的关键演出 |
| 7 | 按玩家路径组织模拟验收，读取主日志；必要时补特定游戏内检查，再部署并记录版本 | 用可重复证据发现逻辑、绑定与交付问题 | 可复现、可说明覆盖范围的发布版本 |

制作中可以交错推进，例如提前画概念图帮助确定主题；但不要用美术已完成替代规则验证，也不要在一个演出里掩盖仍未明确的结算问题。

## 六、用一个设计例子理解三层怎样相互支撑

假设要制作一场“守护者保护同伴，并在承压后反击”的接待。下表是设计示意：

| 层级 | 可制作的内容 | 玩家体验 |
|---|---|---|
| 基础层 | 明确守护对象、承压资源与反击条件；敌方卡组会执行该策略；奖励版保留同一思路并调整强度 | 观察保护关系，选择突破、等待或压制；战后自己尝试这种构筑 |
| 优化层 | 4:3 卡图表现挡在危险前的瞬间；防御皮肤姿势与接触型贴图一致；对白说明立场；核心书页故事解释承诺 | 理解这个角色为何保护别人，画面与规则相互印证 |
| 卓越层 | 第一次关键反击有短暂准备、聚焦、粒子与音乐变化，实际成功后给出声画重音，随后恢复普通节奏 | 机制积累和人物情绪在同一时刻得到回应 |

这个例子的关键是各层共享同一主题。换成刺客、指挥者、演奏者或异想体，动作、视角、节奏和奖励构筑都应随之改变。

## 七、发布前的三层完成检查

### 基础层：玩家能否完整游玩

- 接待条件与入口正确，敌人组合、卡组和阶段符合设计。
- 费用、抽牌、回光、被动、状态、骰子与伤害结算正确，文本可解释实际行为。
- 胜利、失败、重试与退出正常；奖励可获得、可装备、可使用。
- 模组依赖、数据与资源齐全，未误改其他书页或原版共享行为。

### 优化层：内容是否清楚而完整

- 卡图精确横向 4:3，故事和缩略图可读；皮肤大小、方向、底盘与投影正确。
- 特效、动作、声音与真实事件一致，没有重复播放、旧效果残留或关键遮挡。
- 战前、战中、战后剧情以及短台词、配音各走正确入口；核心书页故事能实际读到。
- 角色与书页的身份、风格和文本一致，必要本地化完整。

### 卓越层：玩法扩展与高光是否完整成立

- 原版机制重写有明确的新选择和生效范围，数据、效果、说明与 UI 一致；范围外内容未被误改。
- 异想体书页从选取到实际触发正常，与情感阶段、楼层能力及目标进度相容；相关组合和重试流程已检查。
- 重要时刻有铺垫、焦点和回落，普通行动仍然流畅。
- 粒子、镜头、声音和配乐协同，规则与伤害结果仍可读。
- 镜头、音乐与临时对象有完整恢复；跳过、暂停、失败和退出不会留下状态。
- 正常速度下检查过实际场景；孤立截图、离屏预览和技术校验的范围分别注明。

交付时记录最终候选、构建与资源版本、模拟工程、主日志路径、检查场景及未验证项。编译通过证明代码可构建，文件哈希一致证明部署一致；美术、听感、规则体验和整场稳定性要由相应的实际检查支撑。
