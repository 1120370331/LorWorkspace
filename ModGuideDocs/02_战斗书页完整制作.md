# 战斗书页完整制作操作手册

**多张卡图的构图验收：** 为每张书页单独写动作瞬间、背景场所、镜头景别与角度、画面动线、特效职责，再画缩略草图。统一角色身份与画风，不等于复用同一居中半身、前景拳头或相同烟雾布局。把九张卡排成九宫格并遮住标题，检查主体位置、明暗块、远近与动线是否能区分；再逐张检查肩→肘→腕连续性、手和脸的比例，尤其核对夸张透视下的近手。表情服从角色设定与当前剧情：塔菲案例要求亲近、可爱、自然闭嘴的正式立绘，卡图可按设计憨笑；这不是所有角色一律闭嘴的规则。案例方向见 `AceTaffy/ArtSource/card-direction-v2.md`，其九种镜头仅供学习差异化方法，不是可复用的固定分镜表。

## 二、书页属性详解

### 稀有度 `<Rarity>`

| 值 | 说明 | 卡面颜色 |
|----|------|----------|
| `Common` | 普通 | 绿色 |
| `Uncommon` | 罕见 | 蓝色 |
| `Rare` | 稀有 | 紫色 |
| `Unique` | 独特 | 金色 |

### 距离 `<Spec Range="...">`

| 值 | 说明 |
|----|------|
| `Near` | 近战 |
| `Far` | 远程 |
| `Instance` | 瞬发（对自己使用） |
| `FarArea` | 群攻-清算（不交锋） |
| `FarAreaEach` | 群攻-交锋（逐一交锋） |

### 群攻影响范围 `<Spec Affection="...">`

| 值 | 说明 |
|----|------|
| `Team` | 影响所有敌人 |
| `TeamNear` | 影响附近敌人 |

### 书页选项 `<Option>`

| 值 | 说明 |
|----|------|
| `OnlyPage` | 专属书页（需配合核心书页的OnlyCard，详见下方说明） |
| `ExhaustOnUse` | 使用后销毁（佚亡） |
| `EgoPersonal` | E.G.O个人书页 |
| `Personal` | 个人书页 |
| `NoInventory` | 不在书库显示 |
| `MultiDeck` | 可装备多套卡组 |

### 专属书页设置（OnlyPage + OnlyCard）

专属书页是只能被特定核心书页使用的战斗书页。设置专属书页需要**同时配置两个文件**：

#### 1. 战斗书页 (CardInfo.xml)

在战斗书页中添加 `<Option>OnlyPage</Option>`. `<BookIcon>` 仅用于显示专属图标, 不是功能必填：

```xml
<Card ID="9002005">
  <Name>倾覆万千之流</Name>
  <!-- ... 其他属性 ... -->
  <Option>OnlyPage</Option>
  <BookIcon>10000002</BookIcon>  <!-- 可选: 仅用于显示图标 -->
</Card>
```

#### 2. 核心书页 (EquipPage_Librarian.xml)

在核心书页的 `<EquipEffect>` 标签**内部**添加 `<OnlyCard>战斗书页ID</OnlyCard>`：

```xml
<Book ID="10000002">
  <Name>斯拉泽雅</Name>
  <TextId>-1</TextId>
  <DropTable>2</DropTable>
  <EquipEffect>
    <HP>103</HP>
    <!-- ... 其他属性 ... -->
    <OnlyCard>9002005</OnlyCard>  <!-- 必须在EquipEffect内部！ -->
    <Passive>9002001</Passive>
  </EquipEffect>
</Book>
```

#### 完整示例

假设要为角色"寒霜剑士"(核心书页ID: 10000001) 创建专属书页"绝对零度"(战斗书页ID: 9000099)：

**CardInfo.xml:**
```xml
<Card ID="9000099">
  <Name>绝对零度</Name>
  <Artwork>AbsoluteZero.png</Artwork>
  <Rarity>Unique</Rarity>
  <Spec Range="Near" Cost="4" />
  <Option>OnlyPage</Option>
  <BookIcon>10000001</BookIcon> <!-- 可选 -->
  <BehaviourList>
    <Behaviour Min="8" Dice="15" Type="Atk" Detail="Slash" Motion="S1" EffectRes="" Script="" Desc="" />
  </BehaviourList>
  <Chapter>6</Chapter>
  <Priority>0</Priority>
</Card>
```

**EquipPage_Librarian.xml:**
```xml
<Book ID="10000001">
  <Name>寒霜剑士</Name>
  <TextId>-1</TextId>
  <EquipEffect>
    <HP>100</HP>
    <Break>50</Break>
    <!-- ... 其他属性 ... -->
    <OnlyCard>9000099</OnlyCard>  <!-- 在EquipEffect内部！ -->
    <Passive>9000001</Passive>
  </EquipEffect>
</Book>
```

#### 常见踩坑

- 只有 `<OnlyCard>` 没有 `<Option>OnlyPage</Option>` 时, 书页不会作为专属书页出现.
- 若该书页没有被任何 DropBook 掉落, 又缺少 `<Option>OnlyPage</Option>`, 即使是本体也无法使用.
- `<BookIcon>` 仅用于显示专属图标, 不影响功能. 可省略.

> **注意**：`<OnlyCard>` 必须放在 `<EquipEffect>` 标签内部，否则不会生效！

## 三、骰子属性详解

### 骰子类型 `Type`

| 值 | 说明 |
|----|------|
| `Atk` | 攻击骰子 |
| `Def` | 防御骰子 |
| `Standby` | 反击骰子（被单方面攻击时才触发） |

### 骰子细节 `Detail`

| 值 | 说明 | 图标 |
|----|------|------|
| `Slash` | 斩击 | 斩击 |
| `Penetrate` | 穿刺 | 穿刺 |
| `Hit` | 打击 | 打击 |
| `Guard` | 防御 | 盾牌 |
| `Evasion` | 回避 | 闪避 |

### 动作 `Motion`

需要调整姿势、前摇、出手与收势时，见 [15_书页动作与出刀节奏制作](15_书页动作与出刀节奏制作.md)。`Motion` 选择基础姿势，`ActionScript` 编排逐段动作与反馈时点；`EffectRes` 仍负责本骰攻击素材。

| 值 | 说明 |
|----|------|
| `H` | 打击通用动画 |
| `J` | 斩击通用动画 |
| `Z` | 穿刺通用动画 |
| `G` | 防御动画 |
| `E` | 回避动画 |
| `F` | 远程攻击动画 |
| `S1`~`S9` | 特殊动画（需自定义） |

## 六、装备书页（Instance类型）

装备书页是一种特殊的书页类型，使用后**立即生效**，不需要选择目标，也不参与拼点。游戏中的"不详之力"就是典型的装备书页。

### 与普通战斗书页的区别

| 特性 | 普通战斗书页 | 装备书页 |
|------|-------------|----------|
| Range | `Near` / `Far` | `Instance` |
| 触发方法 | `OnUseCard()` | `OnUseInstance()` |
| 需要选择目标 | 是 | 否 |
| 参与拼点 | 是 | 否 |
| 骰子类型 | `Atk` / `Def` | 通常使用 `Standby` 占位 |

### XML定义示例

```xml
<!-- 装备书页示例：不详之力类型 -->
<Card ID="9000010">
  <Name>能量注入</Name>
  <Artwork>EnergyInject.png</Artwork>
  <Rarity>Uncommon</Rarity>
  <Spec Range="Instance" Cost="0" />
  <Script>MyMod_EnergyInject</Script>
  <BehaviourList>
    <!-- 装备书页通常使用Standby类型骰子作为占位符 -->
    <Behaviour Min="1" Dice="1" Type="Standby" Detail="Hit" Motion="H"
               EffectRes="" Script="" ActionScript="" Desc="" />
  </BehaviourList>
  <Chapter>6</Chapter>
  <Priority>0</Priority>
</Card>
```

### C#脚本实现

**重要**：装备书页必须使用 `OnUseInstance()` 方法，而不是 `OnUseCard()`！

```csharp
// 装备书页效果实现
public class DiceCardSelfAbility_MyMod_EnergyInject : DiceCardSelfAbilityBase
{
    public static string Desc = "[装备时] 恢复3点光芒，下回合失去3点光芒";

    // 装备书页使用 OnUseInstance 而不是 OnUseCard
    public override void OnUseInstance(BattleUnitModel unit, BattleDiceCardModel self, BattleUnitModel targetUnit)
    {
        // unit: 使用书页的单位
        // self: 书页本身
        // targetUnit: 目标单位（装备书页通常为null）

        int currentLight = unit.cardSlotDetail.PlayPoint;
        int recovered = unit.cardSlotDetail.RecoverPlayPointByCard(3);

        // 如果恢复的光芒超过了原有值，下回合失去多余部分
        if (recovered > currentLight)
        {
            unit.cardSlotDetail.LoseWhenStartRound(recovered - currentLight);
        }
    }
}

// EGO装备书页示例
public class DiceCardSelfAbility_MyMod_SelfFlow : DiceCardSelfAbilityBase
{
    public static string Desc = "[装备时] 扣除25点生命值，获得10层[流]";

    public override string[] Keywords => new string[] { "MyFlowKeyword" };

    public override void OnUseInstance(BattleUnitModel unit, BattleDiceCardModel self, BattleUnitModel targetUnit)
    {
        // 扣除生命值
        unit.LoseHp(25);

        // 添加自定义Buff
        // CardAbilityHelper.AddFlowStacks(unit, 10);

        // 或者添加游戏内置Buff
        unit.bufListDetail.AddKeywordBufByEtc(KeywordBuf.Strength, 3, unit);
    }
}
```

### OnUseInstance 方法参数说明

```csharp
public override void OnUseInstance(
    BattleUnitModel unit,        // 使用书页的单位
    BattleDiceCardModel self,    // 书页数据模型
    BattleUnitModel targetUnit   // 目标单位（装备书页通常为null）
)
```

**注意事项**：
- 在 `OnUseInstance` 中使用 `unit` 参数而不是 `this.owner`
- 装备书页的骰子不会实际投掷，只是占位符
- 可以配合 `<Option>EgoPersonal</Option>` 和 `<MaxCooltimeForEgo>` 实现带冷却的EGO装备

## 七、C#书页效果实现

### 书页使用时效果 (DiceCardSelfAbilityBase)

```csharp
// 文件: MyMod_FrostSlash.cs
public class DiceCardSelfAbility_MyMod_FrostSlash : DiceCardSelfAbilityBase
{
    public static string Desc = "[使用时] 获得2层强壮";

    // 使用书页时触发
    public override void OnUseCard()
    {
        owner.bufListDetail.AddKeywordBufThisRoundByEtc(KeywordBuf.Strength, 2, owner);
    }

    // 战斗开始时触发（书页被选中后）
    public override void OnStartBattle()
    {
        // 战斗开始时的效果
    }

    // 战斗结束时触发
    public override void OnEndBattle()
    {
        // 战斗结束时的效果
    }

    // 拼点胜利时触发（攻击方）
    public override void OnWinParryingAtk()
    {
        owner.cardSlotDetail.RecoverPlayPoint(1); // 恢复1光芒
    }

    // 攻击成功时触发
    public override void OnSucceedAttack()
    {
        owner.allyCardDetail.DrawCards(1); // 抽1张牌
    }
}
```

### 骰子命中时效果 (DiceCardAbilityBase)

```csharp
// 文件: MyMod_FrostDice.cs
public class DiceCardAbility_MyMod_FrostDice : DiceCardAbilityBase
{
    public static string Desc = "[命中时] 对目标施加3层束缚";

    }

    // 拼点失败时触发
    public override void OnLoseParrying()
    {
        // 拼点失败的效果
    }

    {

}
```

## 八、本地化文件

### 卡牌名称描述（Localize/cn/BattlesCards/）

```xml
<?xml version="1.0" encoding="utf-8"?>
<BattleCardDescRoot>
  <cardDescList>
    <BattleCardDesc ID="9000001">
      <LocalizedName>寒霜斩击</LocalizedName>
      <Ability>[使用时]获得２层[强壮]。</Ability>
      <Behaviour ID="0">[命中时]施加２层[束缚]。</Behaviour>
      <Behaviour ID="1"></Behaviour>
      <Behaviour ID="2">[命中时]施加３层[束缚]。</Behaviour>
    </BattleCardDesc>
  </cardDescList>
</BattleCardDescRoot>
```

**按真实本地化路径与类型核字段。** 当前 BaseMod 的 `LocalizedTextLoader_New` 查找 `BattlesCards` 目录，注意其中的 `s`；`BattleCards` 不是这条加载链的目录别名。其 `LoadBattleCardDescriptions_MOD_Checking` 使用 `GTMDProjectMoon.BattleCardDescRoot_V2`，根节点为 `BattleCardDescRoot`。条目继承 `LOR_XML.BattleCardDesc`，名称字段为 `LocalizedName`，卡级说明为 `Ability`，骰子说明为带 `ID` 属性的 `Behaviour`。旧写法 `CardDescXmlRoot` 会使整表反序列化失败，条目中的 `Name`、`Desc` 也不能替代上述字段。验收不仅要看 XML 能否解析，还要确认文件可被目录扫描发现，并用实际类型检查每个卡号、名称与说明是否读到预期值。以能力脚本驱动的卡面说明仍须按下节配置 `BattleCardAbilities`，不能仅因本表的 `Ability` 非空就认定所有显示入口已接通。

### 书页内关键词怎样高亮，怎样显示说明

书页文本中的**高亮名称**与悬停书页时的**关键词说明栏**是两条绑定路径，需要分别完成。先写玩家看见的名称，再用稳定 ID 关联说明，不把中文显示名、说明 ID 和能力脚本名混成一项。

#### 1) 在规则文本中标出名称

在实际用于卡级或骰子级说明的 Desc 中写半角方括号，例如：

```xml
<Desc>[使用时]下回合获得２层[霜痕]。</Desc>
```

原版 `TextUtil.TransformConditionKeyword` 会把 `[使用时]`、`[霜痕]` 等片段转换成黄色文字。它是方括号到颜色标记的转换，不会自动根据“霜痕”查找状态 ID，也不会把这段文字变成独立的可点击/悬浮链接。

正文写给玩家看的名称 `[霜痕]`；若写 `[MyMod_FrostMark]`，该 ID 会直接作为文字显示。不要嵌套方括号，也不要用 `【霜痕】`、`［霜痕］` 替代语法标记。

#### 2) 在 EffectTexts 中定义关键词说明

为该关键词建立唯一 ID，并在模组所用的本地化加载目录中保存说明。本项目使用 `Localize/cn/EffectTexts/`，完整结构如下；`effectTextList` 包装层不能省略：

```xml
<?xml version="1.0" encoding="utf-8"?>
<BattleEffectTextRoot>
  <effectTextList>
    <BattleEffectText ID="MyMod_FrostMark">
      <Name>霜痕</Name>
      <Desc>每层使速度－１。生效幕结束时移除。</Desc>
    </BattleEffectText>
  </effectTextList>
</BattleEffectTextRoot>
```

这里是绑定演示，实际状态效果还需代码实现。加载后应能通过 `GetEffectTextName("MyMod_FrostMark")` 和 `GetEffectTextDesc("MyMod_FrostMark")` 取到名称与说明；只有文件放在目录里，不能证明当前语言已正确加载。

#### 3) 把说明 ID 绑定到书页或能力

**方式 A：在 CardInfo 的 Card 节点直接登记。** 对该书页需要解释的每个关键词各写一项，内容是说明 ID：

```xml
<Keyword>MyMod_FrostMark</Keyword>
```

不要写中文名 `<Keyword>霜痕</Keyword>` 来代替 ID，也不要把多个 ID 用逗号塞进一个 Keyword 节点。同一来源不重复登记同一 ID；原生 UI 的直接关键词分支可能因重复字典键报错。

**方式 B：由书页能力或骰子能力的 Keywords 提供。** 脚本已正确注册、当前框架能够解析该脚本时，可在对应能力类中声明：

```csharp
public class DiceCardSelfAbility_MyMod_FrostPage : DiceCardSelfAbilityBase
{
    public override string[] Keywords
    {
        get { return new string[] { "MyMod_FrostMark" }; }
    }
    // 本例只演示关键词声明,实际书页效果另行实现.
}
```

CardInfo 的 Script 对应 `MyMod_FrostPage`；骰子能力同样可在 `DiceCardAbilityBase` 派生类中提供 Keywords。不要为了加说明而另造一个与现有能力无关的脚本，已有脚本直接补声明即可。原生查询存在脚本关键词缓存，修改后应重载候选并检查实际解析结果。

`KeywordListUI.Init` 会收集 CardInfo.Keywords、卡级能力关键词及各骰子能力关键词，再按 ID 查询 EffectTexts，交给 KeywordUI 显示名称和说明。因此：

```text
Desc 的 [霜痕] → 正文名称高亮
Keyword/能力 Keywords 的 MyMod_FrostMark → EffectTexts 同 ID → 名称与解释
状态类 keywordId = MyMod_FrostMark → 状态自身也可引用这份文本
```

说明 ID 与 `keywordIconId` 的图标资源键是不同职责；详见[第 04 章](04_Buff系统与特效.md)。添加说明不会自动施加 Buff 或实现规则；若本模组代码专门读取某个关键词标识，也要保留它已有的机制用途，不能随意借用。

#### 4) 说明文本的显示边界

- 卡级/骰子级规则中使用半角 `[名称]` 高亮，但 `KeywordUI.Init` 本身直接显示 Name 和 Desc，不能假设说明栏里再写 `[另一个状态]` 就会递归高亮或展开另一条说明。
- 原版无参数的 `GetEffectTextDesc(id)` 将 `{0}` 显示为 `X`；传入层数的重载才格式化成具体值。占位符按实际调用设计，不在一般说明栏中随意使用需要额外参数的 `{1}` 等内容。
- 说明栏有槽位容量。优先列出读懂本书页所需的关键词，不把整套模组词典塞进每张卡；检查重复、溢出及普通/详情界面差异。
- 中文正文与玩家可见的说明按项目文案规范使用全角中文标点；`[名称]`、`{0}`、XML 标签、属性及 ID 等机器语法仍保留解析所需的半角字符。全局替换标点前先分离显示文本与机器字段，再验证解析后的实际 UI，不把 `【名称】` 当作高亮标记。

#### 5) 用模拟工程分别验证高亮与说明

在模拟工程中加载当前候选本地化和书页数据，检查：正文中名称变色，说明栏出现正确 Name/Desc；关键词只出现一次；换卡和打开详情后无旧说明残留。主日志至少记录 Card ID、能力 Script、实际收集到的关键词 ID、查到的 Name/Desc、条目数与结果，截图路径也写入同一日志。

若正文变色但没有说明，先检查关键词 ID 是否被收集及 EffectTexts 是否加载；若说明存在但正文没变色，先检查半角括号和文本是否经过 TransformConditionKeyword。缺字段、查到空字符串、槽位溢出或原样显示 ID 都不能算通过。不默认启动游戏，模拟验收与主日志规范见[第 08 章](08_编译与部署.md)。

**源码依据：** `SteriaBuild/Assembly-CSharp/TextUtil.cs`、`KeywordListUI.cs`、`KeywordUI.cs`、`BattleEffectTextsXmlList.cs`、`BattleCardAbilityDescXmlList.cs` 与 `LOR_DiceSystem/DiceCardXmlInfo.cs`。本项目现有 `SteriaFlow` 等 ID 与中文 Name 可作为对应关系参考。

**两条证据分别记录：** 文本解析或 XML 回读只能证明标记和 ID 可解析；还需在实际书页 UI 渲染中看到正文变色、说明栏名称和解释，且各自无重复或溢出。对状态栏的资源合计判断也不要沿用关键词说明栏证据：前者要核实际 Buff 层数及合计规则，后者要核每个独立状态图标显示的自身层数。

## 九、卡图绘制：4:3 故事性构图，以绘图 AI 生成为例

战斗书页的卡图应表现一个能读懂的故事瞬间：谁在什么处境下做了什么，这个行动意味着什么。角色身份、动作、环境与情绪共同服务书页主题。这里制作的是卡牌中显示的插画；卡框、费用、名称、骰子和规则文字由游戏 UI 显示，不画进插画。

**优秀卡图的阅读标准：一眼看出角色是谁、正在做什么动作、发生了什么；仔细看，能发现事件发生的位置、背景关系和叙事细节。镜头本身也要经过设计，具有明确视点、动态和画面感。**

| 阅读层次 | 画面必须交代什么 | 设计时怎样落实 |
|---|---|---|
| 第一眼：角色是谁 | 无需读卡名就能辨认主体 | 保留标志性轮廓、发型、服装、武器和配件；远景、侧背面也要留下足够的身份线索 |
| 第一眼：在做什么动作 | 身体与物件的关系清楚 | 通过重心、肩胯转向、手势、持握和视线让动作成立，关键部位不被特效遮住 |
| 第一眼：发生了什么 | 看得出动作引起或回应的事件 | 交代攻击与阻挡、保护与危险、动作与结果的关系，给出接触点、受力变化或现场反应 |
| 仔细看：在哪里 | 环境具有可辨认的空间与场所线索 | 用地面、建筑结构、地形、光源和前后遮挡建立位置，不让人物悬在无意义的背景上 |
| 仔细看：还有什么故事 | 细节补充处境、人物关系与事件前后 | 选择与已确认设定有关的痕迹、物件、衣装状态和背景反应，细节服务事件而不争夺主焦点 |
| 镜头：为什么从这里看 | 机位帮助表达行动、空间与情绪 | 主动选择景别、角度、透视和前景，形成有特色的观看位置；动态构图中仍保留清晰的角色和因果 |

**卡图的制作方法可以有多种：** 可以手工绘制、委托画师、使用绘图 AI 直接生成，也可以先生成草图再人工修改或结合其他绘画工具完成。根据美术目标和制作条件选择方法；无论采用哪种方法，最终都要满足横向 4:3、故事性构图、角色身份准确和实际卡框可读的要求。

**本节以“绘图 AI 直接生成卡图”为操作示例。在 Codex 中，通过 `imagegen` 调用绘图能力。** 先把故事和构图设计清楚，再提交描述与必要参考图，检查生成结果并迭代。手绘或委托制作也可以沿用前面的设计规范和后面的验收方法。

本节先说明通用设计方法，再介绍 AI 生成流程，并用现有卡图说明设计。角色战斗立绘见[第 12 章](12_战斗单位分层建模与核心书页投影.md)，可播放的贴图特效见[第 13 章](13_贴图攻击特效制作流程.md)。卡图可以为这些效果提供主题，但一张卡图本身不会控制战斗动作或播放时序。

### 第 1 步：先确定交付规格

**做什么：** 新卡图统一使用**横向 4:3，宽:高=4:3**，在构图前确定画幅。

| 属性 | 制作规范 |
|---|---|
| 画幅 | 横向 4:3；精确校验为 `宽 × 3 == 高 × 4` |
| 工作尺寸 | 可用 1024×768、1600×1200、2048×1536；按细节量与资源预算选择 |
| 文件 | PNG；一般绘制完整背景，正常显示区域应不透明，RGB/RGBA 均可 |
| 交付内容 | 单张完整插画，无卡框、UI、标题、费用数字、水印、拼图边线 |
| 发布位置 | 模组根目录下 `Resource/CombatPageArtwork/` |
| 绑定 | 文件名包含扩展名，与 CardInfo 的 `<Artwork>` 完全一致 |
| 来源材料 | 提示词、参考职责、原始生成图和各版修改记录另存源目录 |

这里的 4:3 是本项目的卡图制作要求；不要将整张卡牌 UI 的竖向外形当成插画比例。旧版指南的“330×480”不适用于这里的卡图。宽高接近 4:3 也不等于精确符合，例如 1365×1024 需要在定稿时重新确认画幅。

**为什么：** 卡框会影响最终可见区域，先定画幅才能安排人物、动作与背景；最后强行拉伸会使脸、肢体和武器变形。

**带来什么效果：** 得到可以统一构图、比较和导入的卡图。4:3 是基础约束，关键内容是否被卡框遮挡应优先通过加载原版卡框的模拟工程检查。

### 第 2 步：把书页主题写成一个故事瞬间

**做什么：** 先读角色设定、书页名称、说明与关键机制，用一句话描述画面：

```text
谁，在什么处境下，对什么人或事物，做出什么行动；
画面让玩家感受到什么，哪些可见细节能说明这一点。
```

再填写下面的设计清单。只采用已有设定支持的身份和关系；机制可以转译成画面，但不能凭空补出未确认的剧情。

| 设计问题 | 应写清的内容 | 可用的视觉线索 |
|---|---|---|
| 谁在行动 | 主体身份、不能变化的发型/衣装/武器 | 轮廓、标志配件、持握方式 |
| 在做什么动作 | 一项明确行动，选择准备、接触或余波中的一个时刻 | 身体重心、手势、视线、持握与对象关系 |
| 发生了什么 | 这项行动正在改变或回应什么，保留事件可见的因果 | 被拦下的攻击、改变方向的轨迹、被护住的空间或环境反应 |
| 为什么值得画 | 守护、决断、犹豫、代价、失去或希望等主题 | 表情与动作的张力、危险来源、被保护的空间 |
| 发生在哪里 | 对行动有帮助的场景信息 | 门口、残墙、潮雾、光源等必要环境 |
| 读者先看到什么 | 一个主焦点及少量支撑信息 | 明暗对比、人物姿态、动线与负形 |

先分别写出“第一眼读到的事件”和“仔细看发现的场所与细节”，用视觉主次把两层连接起来。故事性不要求每张图都有多人或复杂背景。单人、局部手势或物件也可以叙事，前提是仍能辨认角色，并看出行动、处境或变化。避免只写“漂亮人物、酷炫光效、史诗感”，也不要把全部骰子和机制逐项画成图标。

**为什么：** 只有人物外貌与特效词汇，容易得到没有事件的摆拍。把行动和情绪说清楚，构图才有依据。

**带来什么效果：** 不依赖卡牌文字，也能读到这张图的主要动作和情绪；结合书页说明时，图像和机制互相解释。

### 第 3 步：按画面问题选择参考图

**做什么：** 先列出本张卡还需要解决的问题，再按职责选图。每张入选参考都应能完成一句话：“这张图帮助我确定……”。角色身份、动作、镜头和画风可以来自不同参考，但每张图负责什么必须明确。

| 参考类别 | 优先选什么图 | 具体看什么 | 不随参考一起带入什么 |
|---|---|---|---|
| 角色身份 | 当前已确认的设定图、清楚立绘、已接受的同角色卡图；必要时补脸部或武器局部 | 发型、脸、衣装结构、配件、武器和色彩识别点 | 旧版设计、临时错误、参考图本身的站姿与背景 |
| 动作与受力 | 对应动作阶段的原版卡图、清楚的动作照片或影视帧；与当前持械方式和接触关系相近 | 肩肘腕、手与武器、身体重心、视线、受力方向 | 参考人物的身份、服装和不属于本角色的武器 |
| 镜头与构图 | 事件关系相近、有明确机位和空间层次的原版卡图、分镜或影视帧 | 视点、景别、透视、前景遮挡、主角与对象的距离、焦点位置 | 整套角色、剧情和场景的照搬；不适合4:3的机械裁切 |
| 画风与视觉层次 | 项目中已接受的卡图，以及想对齐的原版卡图 | 线条、明暗块、边缘虚实、颜色主次、材质笔触、小尺寸辨识度 | 与本卡主题冲突的固有配色、无关标志或已有UI文字 |
| 场所与背景 | 符合设定的环境照片、场景概念图或原版场景 | 建筑/地形结构、地面、材质、光源与空间尺度 | 未确认的地点、时代、阵营标识和背景人物 |
| 关键物件与材质 | 结构清楚的武器、饰品、衣料或相关材质局部 | 形制、连接、握持、纹样和材质响应 | 把局部材质图扩展成整张卡图的构图或画风 |

**选图顺序：** 先固定角色身份，再找能解释动作与事件的参考，然后选择镜头和画风主参考，最后只为缺失的信息补环境或局部图。不必每类都凑一张；同一张图能承担多个职责时，在说明中逐项标出即可。

#### 如何找到并筛掉不合适的图

1. **按动作和机位搜索。** 从本项目已接受素材和原版对应动作开始；还缺资料时，使用“侧后方近景格挡”“低机位前冲”“俯视狭窄通道对峙”等明确描述。仅按角色名或“炫酷卡图”找图，容易重复得到立绘。
2. **看关键关系是否可见。** 用作动作参考的图应看得清手、关节或接触位置。若这些部位被特效遮住、裁掉或画错，就换图；不能因为光效好看而把解剖错误也保留。
3. **匹配事件阶段。** 准备、接触、余波各有不同姿态。同一张卡选择一个明确瞬间；不要把准备姿势、命中反馈和结束后的场景结果无依据地拼在一起。
4. **做4:3与缩略图判断。** 在目标画幅中推演主体位置，再缩小看焦点和身份是否仍成立。参考本身不必是4:3，但要能重新组织进4:3，不能靠挤压人物保留全部内容。
5. **删掉重复与冲突。** 每张图增加一种必要信息即可；多个互相矛盾的机位、光源和身份设计先做取舍。信息不清或只重复已有参考的图不继续叠加。

#### 传给绘图 AI 前，整理参考职责

在生成提示词里先写主导关系：角色长相与服装以当前确认的身份图为准；动作参考只提供受力和姿态；构图参考只提供机位与空间；画风参考只提供笔触和视觉组织。不同参考冲突时，明确选择哪一张的哪一项，不让 AI 自行混合成第三种角色。

建议随源文件保存这样一张参考表，并把对应图片实际作为输入传入：

| 编号 | 文件/来源 | 采用内容 | 排除内容 |
|---|---|---|---|
| 图1 | 当前角色确认稿 | 发型、服装、标志配件与武器 | 原图站姿、空白背景 |
| 图2 | 接触清楚的格挡参考 | 肩肘腕关系、握持与受力方向 | 对方角色外貌与装备样式 |
| 图3 | 侧后方取景的卡图或分镜 | 前景肩部、中景交锋、后景通道的空间组织 | 原图人物、地点标识与剧情 |
| 图4（需要时） | 已接受的项目卡图 | 线条、明暗和细节密度 | 原图的具体事件和必须改变的颜色 |

上表以“已确定要画守住通道的格挡”为示意。实际任务按其设定更换参考，不自动新增通道或对手。可先从少量职责清楚的图开始，只在存在明确缺口时增加。原始参考保留来源和版本；放大裁出的脸、手或武器局部也标明对应原图，避免失去上下文。

如果是在修改已经选定的卡图，要额外标注**哪张是编辑目标**，以及该图的哪些部分已经通过。身份图和画风图作为辅助，不能让它们把已选构图全部替换掉。

**为什么：** 一张“很好看”的图可能只适合参考光色，并不适合当前角色、动作或镜头。按职责筛选，才能减少身份漂移、错误姿态和无关背景的混入。

**带来什么效果：** 绘制者或 imagegen 清楚每张图该学什么；生成后也能逐项对照身份、动作、镜头、画风与场所，定位需要修改的部分。

### 第 4 步：选择有特色的镜头，在 4:3 中组织动态画面

**做什么：** 先用简单草图或文字比较不同机位，选出最能交代角色与事件的一种，再确定主体位置、行动方向、环境和光源。每张卡主动设计镜头，避免把同一张正面站姿不断换背景。

1. **选择最能说明行动的景别。** 手势与表情重要时用近景或半身；需要看支撑脚、挥刀轨迹或人物关系时用更宽的取景。不要为了塞满画面而裁掉关键接触部位。
2. **让动作有对象或结果。** 手与武器、攻击与阻挡、人物与环境之间要有可见关系；画外对象可以用视线、姿态与进入画面的轨迹交代。
3. **用前中后景建立空间。** 主体所在层最清楚，前景可框住视线，背景交代处境。没有叙事作用的碎屑、建筑和光圈可省略。
4. **设置明暗与颜色主次。** 焦点附近对比最明确，辅助区域适度退后。强光不能把脸和握持关系淹没；同一系列保持可识别的色彩与笔触，但各卡动作、镜头和情绪应有区别。
5. **给实际卡框留检查余地。** 人脸、手、武器接触点及关键物件不要无依据地贴边。安全区域以游戏卡框遮罩为准，不把某个固定像素边距当作所有界面的保证。

**镜头怎样选：** 根据要表达的事件选择视点，可以从下面的方法中比较构图方案。

| 镜头选择 | 适合强调什么 | 怎样形成画面感 | 要保住的可读性 |
|---|---|---|---|
| 低机位仰视 | 压迫、决意、向前冲击 | 人物或武器向前延伸，地面与建筑线条强化纵深 | 透视不能把脸、手或武器变成无法辨认的形状 |
| 高机位俯视 | 包围、险境、多人位置与地面后果 | 利用空间分布和投影讲清关系 | 主角不能缩成背景中的一个小点 |
| 肩后、侧后或对手视角 | 对峙、迫近、保护与攻击对象 | 前景局部与中景动作构成临场关系 | 从轮廓、衣装或武器仍能辨认角色，接触位置明确 |
| 贴近动作的特写 | 格挡接触、手势、武器转折或关键表情 | 近大远小、局部出框与精确焦点突出瞬间 | 裁切后仍有角色身份和事件上下文 |
| 斜向构图与透视缩短 | 突进、失衡、急转和力量传递 | 动作线穿过画面，躯干与武器形成方向张力 | 倾斜须与动作和空间一致，不能只把静态画面旋转 |
| 侧向宽景 | 完整动作弧线、双方距离与场所 | 姿态、轨迹和环境线条共同引导视线 | 清楚区分主体、对手和背景的视觉重量 |

“特殊”要落实为一个有理由的观看位置。例如同样画格挡，从主角肩后取景，可以让前景肩部交代身份，中景手与武器显示动作，偏转的攻击显示发生了什么，后景门口或通道说明守住的位置；这个场所须符合当前角色设定。这比单写“电影感、动态镜头”更容易落实。

动态可以来自动作发力、透视、对角线、衣料和环境的响应，不必依赖大面积模糊、速度线或满屏特效。安静的动作也应有明确视点和空间张力。背景可以降低对比或局部虚化，但仍要让仔细看的读者辨出场所和事件线索。

参考原版卡图时，记录它怎样使用景别、剪影、亮暗块、动作动线和环境叙事。学习这些组织方法，再画当前角色的场景；不要把角色战斗散图的“统一朝左、50 PPU”规则套到卡图上，卡图左右方向由构图决定。

**人物比例也按用途分开。** 卡图保持角色的发型、服饰、配色与性格身份，人体比例和透视按该张插画的景别与动作设计。本次 AceTaffy 采用的约三头身、窄躯干、下巴贴衣领和统一挂点属于其战斗模板，不能机械套用到卡图或剧情正式立绘。战斗图的具体测量与约束见[第１２章：原版比例与模板约束](12_战斗单位分层建模与核心书页投影.md#原版比例与模板约束)。

**为什么：** 卡图经常以小尺寸出现，细节堆积会让动作和情绪消失。尺寸缩小后仍成立的大形，比放大后才看清的装饰更重要。

**带来什么效果：** 缩成手牌大小时一眼读出角色、动作和事件；放大时能继续读出发生的位置、背景与细节。镜头赋予这一瞬间独特的视点与动态，画面具有明确的空间和力量关系。

### 第 5 步：以绘图 AI 直接生成为例，使用 imagegen

**做什么：** 选择 AI 生成这条制作路径后，将前面确定的故事、构图、画风和交付规格整理成提示词。可以直接从描述生成完整卡图；需要保持角色身份或统一画风时，再准备相应参考图。查看本地图后，逐张标注它是身份参考、画风参考、构图参考还是要修改的目标图。

在 Codex 中，使用 **`imagegen`** 调用内置绘图工具（工具接口为 `image_gen`）。例如可以提出：“使用 imagegen，根据以下故事瞬间和角色参考，生成横向 4:3 的单幅战斗书页卡图，不含卡框和文字。”新绘制描述场景；有参考图时将图像作为输入；修改已选稿时明确“只改什么、保持什么”。当前工具可用 `referenced_image_paths` 传入本地参考路径；目标图只有会话图像时按工具支持的会话图像引用方式处理，不同时混用两种引用机制。不要把 CLI 的 size、quality 等参数臆写成内置工具的字段。

把 **4:3 横向、完整单幅插画**写入 prompt。若使用明确指定的外部 imagegen API 且它支持精确尺寸，再按该接口的实际 schema 设置尺寸；不能假设所有接口都接受任意 4:3 分辨率。无论通过哪种接口，都检查实际返回尺寸。返回不是 4:3 时，按原构图通过扩图或构图裁切修正，再检查关键人物与物件；不要直接非等比拉伸。

可复用的提示词模板如下。方括号需在调用前替换为本张卡的具体信息：

```text

故事瞬间：[人物]在[已确认的处境]中[具体行动]，情绪是[明确情绪]。
主体身份：[发型、衣装、武器、配件等不可变特征]。
参考职责：[逐张填写身份、动作、镜头、画风或场所职责，和不采用的内容]。
参考主次：[哪些特征以哪张图为准；冲突时保留哪项]。
编辑目标（仅修改已有图时）：[目标图编号、需要改变的内容和已经通过的部分]。
第一眼叙事：[角色是谁、做什么动作、正在发生什么事件]。
镜头与构图：[景别、具体视点、机位角度、透视、主体与行动对象的关系]。
选这个镜头的理由：[它怎样强化本次行动、情绪或空间关系]。
动态来源：[发力方向、透视缩短、衣料/环境响应等实际画面关系]。
动作关系：[视线、肩肘腕、持握、接触点、重心或运动方向]。

保持：[已经确定且不能漂移的设计]。
```

没有某类参考时删掉相应行；不要写“参考图1”却未实际传图。卡图通常需要完整场景背景，不沿用角色部件或特效素材的绿底/品红色键要求。

**为什么：** 角色参考和画风参考负责不同约束，混在一起容易改错身份或照搬整个构图。明确输出用途和比例，也能减少生成整张卡牌 UI、透明角色或九宫格的误差。

**带来什么效果：** imagegen 得到可执行的画面设计，产出能进入本项目制作流程的插画；调用成功后仍需检查实际图像。

### 第 6 步：先审故事和构图，再做局部迭代

**做什么：** 先看缩略图，再看原图，按以下顺序检查：

- **第一眼检查：** 暂时不看卡名和说明，在手牌大小下能否认出角色、说出动作和发生的事件；不能只认出一个发光的人形。
- **仔细看检查：** 放大后能否辨认发生的位置，背景和细节是否补充事件或人物处境，而不是无关装饰。
- **镜头检查：** 能否说明为什么选择这个机位，透视、前景、动线是否带来动态和临场感，同时没有损害身份与动作辨识。
- **参考一致性检查：** 人物身份是否符合确认稿，动作和镜头是否采用指定关系，有没有把参考人物的衣装、场景标识或错误结构一起带入。
- 人物身份、服装、武器、手指、持握和透视是否正确。
- 主焦点、动作关系和背景是否清楚，有没有无关人物或未确认的剧情元素。
- 实际宽高是否精确 4:3，是否出现黑边、假卡框、文字、水印或透明缺口。
- 缩小后人物与特效是否混成一团，同系列是否过度重复相同姿势和镜头。

一次围绕一个明确问题修改，并重申已经通过的部分。例如：“只降低背景光团亮度，保留人物身份、合掌动作、机位和4:3构图，让脸与手重新可读。”结构性问题应改构图或姿势，不能只增加分辨率和光效。

原始生成图、选定版本与最终输出分开保存，记录实际提示词、参考文件与职责、生成方式、返回尺寸、修改内容及最终哈希。源图保存在制作目录；最终引用的图片必须进入工作区，不能只留在生成工具缓存中。

**为什么：** 先修细节、后改构图会返工；没有版本记录则容易丢掉已经接受的身份和画面关系。

**带来什么效果：** 每次迭代都解决一个可见问题，最终卡图有明确的选择依据和可追溯来源。

### 以「潮雾晨光」为例：把主题落实为画面

### 第 7 步：导出、绑定并在真实卡框中验收

**做什么：** 将定稿导出为 PNG，放到 `Resource/CombatPageArtwork/`，在对应 Card 节点设置：

**为什么：** 文件正确、XML 正确和实际显示正确是三个独立检查点；生成预览不会告诉你游戏卡框如何遮挡构图。

**带来什么效果：** 最终插画既表达书页故事，也能通过正确资源名在游戏中稳定显示。

## 十一、抽牌与牌区流转机制(官方规则)

- 抽取书页来自抽牌区. 手牌已满8张时不再抽取(可利用已装备书页配合卦象规避抽卡限制).
- 书页在装备时同时进入使用区与保留区. 使用时从使用区移除. 含反击的书页在战斗开始时移除. 与群攻进行拼点的书页会在拼点时移除.
- 幕结束时, 仍在使用区中的书页会在使用区中移除, 然后将书页置入手牌区. 保留区中剩余书页置入弃牌区.
- 战斗过程中被丢弃的书页直接置入弃牌区.
- 抽牌时, 书页逐张从抽牌区抽取. 抽牌区书页数为0时暂停抽牌, 将弃牌区中的书页洗入抽牌区后继续抽取.
- 我方本幕使用的书页在幕结束后才会洗入弃牌堆, 待触发洗牌后进入抽牌区等待抽取. 因此无特殊说明的使用时抽取, 不会直接抽到本幕打出的书页.
- 高贵的下一幕多抽可规避本问题. 在卡组中加入平心静气可保证五情感之后的每幕满手牌. 平门.
- 类似效果还有封喉一刺被动能力2.png抽洗控牌.

## 十二、骰子伤害与结算机制(官方规则)

### 1) 结算公式与顺序

- 最终伤害公式:
  (骰子点数 + 伤害增加 - 伤害减免) x (百分比增伤之和) x 百分比减伤 x 目光 x 抗性 - 刀枪不入 = 最终伤害
- 顺序理解: 先准备武器(加减 buff), 再打出招式(百分比增伤), 最后命中防弹衣(刀枪不入).
- 对混乱状态下敌人无法造成混乱伤害.
- 对因机制处于固定体力的敌人无法造成伤害, 混乱伤害或追加伤害.
- 对免疫抗性敌人仅可造成追加伤害.

示例:
6~10斩击骰出9, 自身斩击伤害+3, 对方有集火, 刀枪不入与1层易损, 斩击抗性为耐性.
伤害为(9 + 3 + 1) x 1.5 x 0.5 - 1 = 8.75, 向下取整造成8伤害.

### 2) 基础伤害值

- 基础伤害值为攻击骰子或反击攻击骰子投出的点数, 经过威力加成结算后显示的点数.
- 这是决定受伤多少的原始参数, 与伤害抗性, 伤害 buff 共同计算最终伤害.
- 基础伤害值分为3种: 斩击, 突刺, 打击.

### 3) 伤害抗性

- 伤害抗性是第二个参数, 与基础伤害值和伤害 buff 共同决定最终伤害.
- 伤害抗性共有36种, 斩击/突刺/打击分别从体力与混乱抗性层面各有6种.
- 陷入混乱时, 若无特殊说明则所有抗性变为致命.

伤害抗性总览(红色为体力抗性, 黄色为混乱抗性):
- 致命: 受伤2.00. 图标: S致命.png, SB致命.png, P致命.png, PB致命.png, H致命.png, HB致命.png.
- 脆弱: 受伤1.50. 图标: S脆弱.png, SB脆弱.png, P脆弱.png, PB脆弱.png, H脆弱.png, HB脆弱.png.
- 一般: 受伤1.00. 图标: S一般.png, SB一般.png, P一般.png, PB一般.png, H一般.png, HB一般.png.
- 耐性: 受伤0.50. 图标: S耐性.png, SB耐性.png, P耐性.png, PB耐性.png, H耐性.png, HB耐性.png.
- 抵抗: 受伤0.25. 图标: S抵抗.png, SB抵抗.png, P抵抗.png, PB抵抗.png, H抵抗.png, HB抵抗.png.
- 免疫: 受伤0.00. 图标: S免疫.png, SB免疫.png, P免疫.png, PB免疫.png, H免疫.png, HB免疫.png.

例:
某一斩击骰子投出39, 受击方斩击抗性为耐性, 斩击混乱抗性为抵抗, 无其他伤害 buff.
则扣除39 x 0.50 = 19.5点体力, 39 x 0.25 = 9.75点混乱抗性.

### 4) 伤害 buff

- 伤害 buff 是第三个参数, 与基础伤害值, 伤害抗性共同决定最终伤害.
- 伤害 buff 描述通常为: 斩/突/打伤害+X, 或造成/受到的伤害+X%.
- 被动能力4.png黎明之火等被动的追加伤害, 不计算入伤害增加或减少.

### 5) 追加伤害

- 追加伤害描述通常为: 命中/拼点胜利时, 追加X点伤害或混乱伤害.
- 追加伤害不受除刀枪不入之外的任何伤害增减效果影响, 直接扣除体力或混乱.
- 追加伤害不参与抗性乘算, 但仍不能绕过固定体力机制.
- 诺沃面料无法抵挡追加伤害.
- 追加伤害紧跟在骰子伤害之后显示, 伤害为红色, 混乱伤害为黄色. 被完全阻挡时显示对应颜色的-0.

## 十三、拼点与单方面攻击(官方规则)

### 1) 拼点(Clash)

- 定义: 双方骰子投掷后比较点数大小, 决定由哪方造成伤害的比较机制. 拼点书页在界面中显示为黄色实线双箭头.
- 发生条件: 双方书页互相指向, 对应速度骰子相遇时触发拼点.
- 拼点胜负可获得情感硬币(详见情感规则).
- 不同类型骰子的拼点规则请参考对应页面: 进攻型骰子拼点, 防御型骰子拼点, 反击型骰子拼点.
- 范围书页不进行拼点, 故无法通过摧毁骰子获得情感硬币.
- 远近交互规则:
  - 除反击外, 近战书页骰子与远程书页骰子拼点胜利时不立刻造成伤害.
  - 该骰子会被置于当前书页末尾, 待远程书页的攻击骰子耗尽后, 作为单方面攻击重新投掷并造成伤害.
  - 先制近战书页(如赤瞳, 血清-W等)与远程书页拼点时视为远程书页, 与近战书页拼点时视为近战书页. 详情见书页类型规则.

### 2) 单方面攻击(One-sided Attack)

- 定义: 当某速度骰子攻击另一速度骰子时, 对方未装备书页, 或书页未指向该速度骰子, 或该书页仅含反击骰子. 单方面攻击显示为蓝/红色实线单箭头.
- 发生条件补充:
  - 两速度骰子互相瞄准但一方或双方装备群体书页时, 准备阶段会显示为单方面攻击, 但实际上既不视为拼点, 也不视为单方面攻击(无法触发拼点相关效果).
  - 若准备阶段互相瞄准, 但在拼点发生前一方书页被摧毁(如血雾弥漫), 视为单方面攻击.
  - 若书页仅含反击骰子, 则战斗开始时该速度骰子视作未装备书页.
- 结算流程:
  - 单方面攻击时, 先与对方反击骰子库中的骰子进行拼点.
  - 反击骰拼点胜负同样可获得情感硬币.
  - 若无反击骰或反击骰已消耗, 则直接对目标造成伤害, 伤害遵循抗性等结算规则.
  - 己方书页中的防御型骰子会置入反击骰子库.

### 3) 制作要点

- 书页与骰子文本中区分"拼点胜利/失败"与"命中时"十分关键.
- 若希望效果只在拼点成立时生效, 使用"拼点胜利"类触发.
- 若希望效果在单方面攻击中也能生效, 使用"命中时"类触发.
